> **V1.1.1 修订边界（ground-truth 审计契约，当前实现范围）：**本版把既有只有 `action/object/time` 的服务端 `audit_events` 增强为可还原人工标注过程的追加式（append-only）富审计日志，用于马上进行的人工标注与后续机器预筛评估的 ground truth。范围与边界：一、契约细节见 §4.4.6；二、疑点动作必须区分 `create_issue / update_issue / resolve_issue / reopen_issue / delete_issue`，删除前完整记录保存在 `before`，`after` 为 null；三、字幕段动作按实际前后差异分类为 `edit_segment_text / confirm_segment / unconfirm_segment / update_segment_timing / update_segment`，`changedFields` 必须准确，`originalText` 继续不可改；四、当前没有账号体系，不伪造真人身份：客户端携带持久但非实名的 client instance ID 与明确 source，`clientId` 可区分客户端实例但不代表经过认证的人；五、只提供只读查询 API `GET /api/projects/:projectId/audit-events`，不提供修改或删除审计事件的 API；六、旧 SQLite 数据库原地、幂等、无损迁移，不 drop/recreate 表、不丢旧事件；七、本轮不要求审计 UI，接口与数据库供后续 ground-truth 导出使用。除审计能力外，播放、编辑、疑点、跨设备与 revision/409 语义全部保持不变。

> **V1.1.2 修订边界（审计契约精确语义，主审计复核）：**本版不新增范围，只把 V1.1.1 契约中含混的语义钉死并实现：一、**语义 no-op**：与当前持久值完全相同的 segment/issue 写入、以及分阶段补丁相互抵消后净状态无变化的 media 更新，都是成功但无变化的请求——不写对象、不增长 revision、不产生审计事件，返回当前对象与当前 revision；media 的 changedFields 在全部补丁应用并 canonical 后一次性基于最终前后值计算，顺序稳定且绝不重复；二、**canonical after**：疑点写接口返回值与审计 `after` 一律取自数据库最终行（如请求省略 `resolvedAt` 时，持久行、返回值、审计 after 三处一致为 null），不得暴露请求原对象；三、**createdAt 不可变**：已有疑点的 `createdAt` 是创建时间，更新请求与其不一致时 400 回滚（无写入、无事件、无 revision 变化）；四、**issue_id 全局隔离**：`issues.issue_id` 为全局主键，写入前必须校验既有同名疑点的项目归属，跨项目冲突返回 404 且双方数据、revision、审计零污染；导入/迁移新项目时与既有项目 issueId 碰撞、或同一载荷内重复 issueId，都使整个创建事务回滚，`create_project` 快照计数取实际插入值、与主表一致；五、**schema 版本只进不退**：数据库 `user_version` 高于当前程序支持版本时拒绝打开（保持版本、表和数据不变，不降级、不执行当前 schema DDL，释放句柄并明确报错）；数据库打开后任何初始化异常（读取版本、PRAGMA/SCHEMA/迁移、语句预编译等）同样统一释放句柄后原样重抛；六、**损坏即失败**：审计查询遇到非 SQL NULL 且无法解析或类型不符的 JSON 字段时明确失败并暴露数据损坏，不得静默伪装成“历史未记录”。

> **数据安全边界：**服务端写入必须携带项目版本（`revision`/`If-Match`/`expectedRevision` 之一）；版本过期返回冲突，不允许后写入静默覆盖前一台设备的校对稿。服务不可用时保留当前内存草稿和待提交队列，不切换到另一份“本地历史”冒充已同步数据。旧浏览器 IndexedDB 数据迁移必须幂等、可重试、成功前不删除原数据，也不上传 MP3 正文。

> 一句话定义：听校是一款以服务端项目空间为事实源、以浏览器/桌面客户端为工作界面的长音频校稿工作台，把原音、机器转写、人工校对稿和可出版成稿保持在同一条可追溯时间线上，让用户用键盘完成“听、改、存疑、复核、成稿、验收、导出”的完整闭环。

# 一、概述（为什么做）

## 1.1 产品概述及目标

### 1.1.1 背景介绍

用户当前拥有一批长时课堂录音及机器转写，希望通过人工听校得到准确、完整、可读、可追溯的最终文稿。传统做法是在音频播放器、SRT 文件和文本编辑器之间来回切换，主要问题不是“没有编辑器”，而是听音、定位、修改、存疑、复核和成稿彼此脱节：

1. 音频较长，反复拖动播放器难以精确回到同一句。
2. 声音不清楚时，需要降速、回退、循环和增强，但普通播放器操作成本高。
3. 机器字幕会出现错词、断句、标点、专名、水印和漏转；仅通读文字无法发现漏掉的声音。
4. 修改 SRT 容易破坏时间轴，最终书稿又需要重新排段、去口语和组织章节。
5. 对听不清的内容，人容易凭上下文“猜”；若不保留疑点和证据，后续无法可靠复核。
6. 工作跨度长，没有自动保存、进度记录和版本快照时，容易丢改动或重复劳动。
7. 成稿中的结论如果不能回到原音时间点，无法审计其准确性。
8. 同一服务被不同设备访问时，项目必须共享同一份进度；如果项目事实源落在浏览器本地，换设备会看到另一份空历史，用户会误以为项目或校对稿已经丢失。

本仓库中的真实材料确认了上述问题及规模：

| 项目 | 当前实况 | 对产品设计的影响 |
| --- | --- | --- |
| 音频 | 21 份 MP3，合计 66:08:49.916，约 1.77 GiB | 必须支持批量导入、超长音频、后台索引和断点续做 |
| 单文件 | 抽样文件时长 03:24:50.090，64 kbps、44.1 kHz、单声道；全量中存在 5 小时以上文件 | 波形不能一次性全量渲染；播放和定位必须稳定 |
| 字幕 | 21 份 SRT，共 24,671 个字幕段 | 必须支持大规模分段编辑、搜索、合并与拆分 |
| 文件命名 | MP3 与 SRT 的空格数量不一致，如“青创 一   1 … .mp3”与“青创 一 1 … .srt” | 导入时要规范化文件名并自动配对，冲突时人工确认 |
| 转写质量 | 存在 TurboScribe 水印、错词、跨字幕断句、标点不统一和口语冗余 | 需要规则检查、术语表和原稿/校对稿分层 |
| 覆盖差异 | 音频合计时长比现有 SRT 账本末尾合计多 00:07:08.606 | 不能以“最后一条字幕已改完”代替全音频覆盖验收 |
| 下游用途 | 已有 Markdown 书稿、章节账本及精确来源时间范围 | 成稿必须保留来源文件与毫秒级时间范围，并支持仓库格式导出 |

旧方案是“播放器 + 文本编辑器 + 人脑记进度”。用户已经在实际校稿，需求来源明确，且现有素材足以作为产品验收数据。成功与否不以“用了 AI”衡量，而以校对覆盖率、剩余疑点、可追溯性和人工耗时衡量。

### 1.1.2 产品概述

听校采用“三层文稿、一个证据轴”：

| 层级 | 是否可改 | 作用 | 质量要求 |
| --- | --- | --- | --- |
| 原始识别层 | 否 | 保存导入时的 SRT 原貌，作为机器结果基线 | 字节级保留，可随时对照 |
| 逐字校对层 | 是 | 忠实记录原音，改正错词、断句、标点和说话人；保留有意义的口语信息 | 每一段均绑定原音时间范围和人工状态 |
| 成稿层 | 是 | 在不改变原意的前提下去口语、重组段落、配置标题和章节 | 每一段均能回溯到一个或多个已确认校对片段 |

~~~mermaid
flowchart LR
    A[原始音频：唯一事实来源] --> B[原始识别层：只读]
    A --> C[逐字校对层：忠实听校]
    B --> C
    C --> D[成稿层：可读性编辑]
    C --> E[疑点与术语库]
    E --> C
    D --> F[质量闸门]
    C --> F
    F --> G[SRT / TXT / Markdown / JSON 导出]
~~~

**[假设 A1]** 首个可用版本由一个绑定 `0.0.0.0` 的本地服务提供，桌面或浏览器客户端通过同一服务访问；服务端默认只在用户控制的机器/局域网内运行，不要求公网账号。项目结构化数据保存在服务端，源 MP3 默认仍由各设备本地选择或重定位。

**[假设 A2]** 用户需要的不只是修正 SRT，而是同时得到“可核对的逐字校对稿”和“可阅读的最终成稿”；两层必须分开，避免为了行文好看而污染事实记录。

### 1.1.3 产品目标

#### 业务目标

本项目是内部生产力工具，业务目标是把一次性的人工校稿过程沉淀为可重复、可验收的生产流程。

| 目标 | 指标定义 | V1.0 目标值 | 评估方式 |
| --- | --- | --- | --- |
| 完成全量材料校对 | 已通过质量闸门的有效语音时长 ÷ 检出的有效语音总时长 | 100% | 以 21 份音频为首个生产项目 |
| 消除“静默漏稿” | 未处理的“有语音、无文字”候选区间数 | 0 | VAD 候选逐条确认：补录、非语音或可接受缺失 |
| 保证成稿可追溯 | 有有效来源映射的成稿段落数 ÷ 全部成稿段落数 | 100% | 导出前强校验 |
| 控制未决问题 | 阻塞级未解决疑点 | 0 | 质量闸门不允许带阻塞疑点完成 |
| 提升人工效率 | 同一难度样本下，每音频小时的人工校稿耗时 | 相比“播放器 + 文本编辑器”降低至少 30% | 首次用 60 分钟分层抽样建立基线 |
| 防止数据丢失 | 因崩溃导致的已输入内容丢失窗口 | 不超过 5 秒 | 崩溃恢复测试 |

**[待确认 C1]** “效率提升至少 30%”是建议目标；正式基线尚未测量。建议从清晰、一般、困难片段各抽 20 分钟，记录旧流程与听校流程的净操作时间后确认。

#### 用户目标

| 目标用户 | 用户目标 | 衡量指标 |
| --- | --- | --- |
| 主校对者 | 不离开工作台即可听清、修改并确认当前句 | 90% 以上常用操作可由键盘完成；从暂停到重听不超过一次按键 |
| 主校对者 | 随时知道做到哪里、还剩什么 | 文件、时长、字幕段、疑点四种进度均可见 |
| 复核者 | 快速定位疑难处，不重听整份音频 | 点击疑点后 2 秒内开始播放带上下文的原音 |
| 成稿编辑者 | 改写时不丢失原意和出处 | 每个成稿段落可一键回放全部来源范围 |
| 项目负责人 | 只有达到明确质量标准时才宣告完成 | 完成状态由系统质量闸门计算，不能仅手动勾选 |

#### 北极星指标

**已人工确认且可追溯的有效语音分钟数。**

该指标同时要求“听过”“确认过”“能回到原音”，比字数、文件数或打开应用次数更接近真实产出。

#### “完美文稿”的操作性定义

本 PRD 不把“完美”定义为主观的零瑕疵，而定义为以下可验收条件全部成立：

1. 检出的有效语音区间全部被人工覆盖。
2. 逐字校对层无机器水印、无未处理的时间轴错误、无阻塞疑点。
3. 所有无法从原音确定的内容均明确标记，不以猜测冒充原话。
4. 成稿层通过项目风格规则，且每段有来源映射。
5. 导出文件可重新导入，时间轴、文本和状态不丢失。
6. 用户对质量报告签署“完成”。

声音中已经永久缺失的信息无法被软件恢复。因此，“原音确实不可辨”是合法结论；诚实标注比编造一个流畅答案更接近完美。

### 1.1.4 目标用户

| 角色 | 特征 | 当前做法 | 核心诉求 |
| --- | --- | --- | --- |
| 主校对者 | 熟悉中文内容，长时间听写与修订 | 播放器和编辑器来回切换 | 快捷播放、精确定位、无损编辑、不中断心流 |
| 复核者 | 对课程术语、人物或背景更熟悉 | 收到零散问题后单独找音频 | 集中处理疑点、看到上下文、留下结论 |
| 成稿编辑者 | 负责把口语整理成书面稿 | 从 SRT 或片段复制粘贴 | 双栏对照、来源绑定、章节组织、规则检查 |

# 二、产品描述（做什么）

## 2.1 产品需求描述

### 2.1.1 核心产品原则

1. **原音优先**：AI、字幕、术语表都只能辅助，不能覆盖人的最终判断。
2. **不隐藏不确定性**：听不清必须成为可分派、可复核、可签署的问题，不能默默猜测。
3. **证据稿与成稿分离**：逐字准确和行文流畅是两个不同目标，分别编辑、相互映射。
4. **时间轴即证据链**：每次修改、疑点、成稿段落和导出都能回到来源时间范围。
5. **键盘优先、鼠标可用**：高频动作可连续操作，所有快捷键可查看和自定义。
6. **服务端为事实源**：项目和进度由同一服务端持久化；客户端可缓存，但不能把浏览器存储当作项目归属。
7. **长任务可恢复**：自动保存、断点续做、版本快照和后台任务状态是基础能力。
8. **完成由标准决定**：文件名变成“final”不代表完成，质量闸门通过才代表完成。
9. **历史行为可预期**：历史列表不得用单一最近项目掩盖其他项目；存储边界作为内部实现约束记录，不在主界面展开技术说明。

### 2.1.2 V1.0 范围

| 范围内 | 范围外 |
| --- | --- |
| 本地项目与文件夹批量导入 | 在线音频录制 |
| MP3 + SRT 的自动配对和手工修正 | 完整数字音频工作站能力 |
| 长音频波形、精确跳转、循环、降速、增益、语音增强预设 | 对源音频做母带级修复 |
| 原始识别、逐字校对、成稿三层模型 | 自动生成“无需人审”的最终文稿 |
| 字幕改字、分段、合并、时间调整、说话人 | 影视字幕视觉排版 |
| 疑点队列、术语表、上下文搜索 | 公共术语市场 |
| VAD 覆盖候选与质量闸门 | 把 VAD 判断当作绝对真值 |
| Markdown、SRT、TXT、JSON 和项目快照导出 | 直接发布到第三方出版平台 |
| 当前书稿来源格式适配 | 自动决定全书观点与编辑立场 |
| 同一服务端项目空间的多项目历史、逐项目继续工作与跨设备共享 | 公网账号/RBAC、多人实时推送、云 ASR 和服务端托管源 MP3 |

### 2.1.3 默认校对规范

逐字校对层：

- 修正识别错词、同音词、标点和明显断句。
- 保留改变语气或含义的重复、否定、自我修正。
- “嗯、啊”等无语义填充词是否保留由项目样式配置；默认保留在逐字层，成稿层删除。
- 掌声、笑声、音乐等用统一标签表示，如“[掌声]”。
- 数字先忠实记录听到的表达；成稿层再按风格统一。
- 无法判断时创建疑点；不得只凭“读起来顺”替换。

成稿层：

- 可删除纯课堂互动、口头禅和无意义重复。
- 可调整句序和段落，但不得新增来源中不存在的事实或观点。
- 事实性补充必须标记为“编辑注”，不能伪装为讲者原话。
- 每个段落至少绑定一个来源范围；跨文件段落可绑定多个范围。

**[待确认 C2]** 建议以“忠实校对稿 + 可读成稿”作为默认交付；若最终只要逐字稿，可关闭成稿模块，但这会改变 V1.0 范围和验收项。

数据边界：

- 源音频和源字幕只读。
- 服务端数据库保存项目元数据、原始 SRT、各层文本、状态、疑点、播放位置、项目版本和审计事件；源音频路径按设备记录，不能把某一设备的文件句柄当作共享数据。
- 浏览器 IndexedDB 只可作为缓存或旧版本迁移来源，不能作为生产环境的项目事实源。
- 缓存可删除并重建，不是唯一数据源。
- 导出写入新文件；默认不覆盖任何源文件。

## 2.3 全局说明

### 2.3.1 全局异常处理

| 异常场景 | 处理方式 | 用户提示 |
| --- | --- | --- |
| 源文件被移动或改名 | 项目标红但保留全部编辑；允许“重新定位文件”并校验哈希 | “找不到源音频。请选择其新位置，现有校稿不会丢失。” |
| 源文件内容变化 | 禁止静默替换；展示旧、新哈希和时长，要求作为新版本导入 | “文件内容已变化，不能继续沿用原时间轴。” |
| SRT 解析失败 | 显示行号与原因；允许以纯文本导入或跳过 | “第 418 行时间格式无效，请修复或选择降级导入。” |
| 音频解码失败 | 保留项目条目；支持重试、重新定位或转码代理 | “音频暂时无法解码，原文件未修改。” |
| 波形/VAD/增强失败 | 不阻塞原音播放与文本编辑；后台任务可重试 | “分析失败，可继续用原音校对。” |
| 磁盘空间不足 | 立即停止写缓存；优先保证数据库提交；提供清理缓存入口 | “空间不足，已暂停生成缓存；校稿已保存。” |
| 数据库写入失败 | 编辑器进入只读保护，保留内存草稿并提供另存恢复包 | “保存失败，请不要关闭应用；可导出紧急恢复包。” |
| 应用崩溃 | 重启后自动打开恢复页，展示最后持久化时间和未完成后台任务 | “已恢复到 14:32:05，最多可能缺少最后 5 秒输入。” |
| 导出目标已存在 | 默认生成带版本号的新文件；覆盖需二次确认 | “文件已存在。建议导出为 V003。” |
| 权限不足 | 不修改目标；允许改选目录 | “无法写入此目录，请选择有权限的位置。” |
| 可选云服务不可用 | 保留本地工作流；任务进入失败队列，不自动重传私密内容 | “外部服务不可用，本地校对不受影响。” |

- 全局搜索不得因当前筛选隐藏匹配结果。
- 时间范围统一显示为 HH:MM:SS.mmm；输入可省略毫秒，但保存时补齐。
- 项目入口的“最近项目”按 `updated_at` 倒序展示同一服务端工作空间的全部项目（默认最多展示 20 条，超过后可加载更多）；每条至少显示项目名、已保存播放位置、最近更新时间和“打开”操作。
- “继续上次校对”只能作为列表标题或最近项目的快捷入口，不得把其他项目隐藏在单一卡片中；点击任意项目只打开对应服务端 `project_id`，不覆盖或重置其他项目。
- 历史为空时只显示简短空状态（例如“暂无最近项目”），不在主界面展示 origin、IndexedDB、设备隔离或同步诊断文字。

### 2.3.3 全局交互

| 场景 | 交互要求 |
| --- | --- |
| 自动保存 | 文本输入停止 500 ms 后提交；状态栏显示“保存中 / 已保存 HH:MM:SS / 保存失败” |
| 撤销/重做 | 文本、分段、时间轴、状态操作均进入统一历史；跨会话通过版本快照恢复 |
| 删除 | 删除字幕段、成稿段落或疑点前显示影响；源层不可删除 |
| 异步任务 | 显示队列、进度、预计剩余和失败原因；不以全屏遮罩阻塞校对 |
| 跳转 | 从搜索、疑点、成稿来源跳转时，保留返回位置 |
| 播放跟随 | 当前字幕高亮并自动滚动；用户以鼠标拖动原生滚动条、点击滚动轨道、使用滚轮或触控板时，立即暂停自动跟随，人工滚动优先；提供“一键回到播放点”恢复跟随 |
| 条目定位 | 点击字幕条目的非操作区域或聚焦该条校对文本框，即选中该段并把播放头精确定位到 `start_ms`；若旧段正在播放，先暂停；定位后不自动播放 |
| 播放边界 | 普通播放始终绑定当前选中段，只允许在 `[start_ms, end_ms]` 内出声；到 `end_ms` 自动暂停，不得串入下一段；显式开启当前段循环时才允许回到段首继续 |
| 底部音频工具栏 | 只保留时间显示、播放速度、自动回退、循环，以及播放跟随关闭时出现的“回到播放点”；不显示独立播放/暂停、后退 2 秒、前进 2 秒按钮，也不显示无实际控件的“选中策略”文字；后退/前进 2 秒只在字幕行内提供；时间轴继续保留在工具栏上方 |
| 项目历史 | 显示同一服务端工作空间内多个最近项目；设备 A 创建的项目在设备 B 访问同一服务时可见；每条记录独立打开并恢复自己的片段、播放位置和保存时间 |
| 服务状态 | 服务端不可用时保留当前内存草稿和待提交队列，显示简短保存失败状态；不得静默切换到另一份本地历史或假装已同步 |
| 并发写入 | 每次写入携带 `revision`/`If-Match`；版本不一致返回 409，保留本地草稿并要求刷新/比较后重试 |
| 焦点 | 编辑器聚焦时，普通空格输入文字；全局播放使用 F8，避免抢占文本输入 |
| 提示 | 成功操作使用轻提示；破坏性或不可逆操作使用确认弹窗 |
| 颜色 | 状态除颜色外同时使用图标和文字，满足色觉障碍用户 |
| 时间轴拖动 | 拖动时实时预览时间；松手才提交；Esc 取消 |

### 2.3.5 全局数据与时间规则

- 内部时间统一存储为整数毫秒，界面和导出按格式转换，禁止浮点累计误差。
- 字幕段满足 0 ≤ start_ms < end_ms ≤ audio_duration_ms。
- 相邻段默认允许间隙，不允许重叠；若确有多人同时说话，可显式标记“允许重叠”。
- 所有对象使用不可变 UUID；合并、拆分后保留来源关系，不复用已删除 ID。
- 所有修改记录 UTC 时间和本地时区；界面按 Europe/Zurich 或用户设置显示。
- 文件哈希建议使用 SHA-256；大文件导入时后台计算，不阻塞首次播放。

# 三、功能需求（怎么做）

## 3.1 项目创建、导入与文件配对

### 3.1.1 描述

把一组本地音频、字幕和可选参考资料建立为可恢复的校稿项目，自动完成文件识别、配对、完整性检查和后台索引。

### 3.1.2 用户故事

- 作为项目负责人，我希望选择“环境画卷”目录后一次导入全部 MP3 和 SRT，以便不用逐一建文件。
- 作为主校对者，我希望系统能识别文件名中多余空格并正确配对，以便不会把音频和错误字幕对应起来。
- 作为项目负责人，我希望应用发现源文件被替换时立即提示，以便旧时间轴不会悄悄套到新录音上。
- 作为主校对者，我希望导入后立刻开始听第一份音频，而波形和语音检测在后台继续，以便不用等待全部预处理完成。

### 3.1.3 前置条件

| 类型 | 条件 |
| --- | --- |
| 文件 | 用户对源目录至少有读取权限 |
| 存储 | 服务端项目数据目录可写；客户端有足够空间保存本地音频缓存和未提交草稿 |
| 格式 | V1.0 必须支持 MP3 音频和 UTF-8 / UTF-8 BOM SRT |
| 环境 | 本地音频解码组件可用 |

### 3.1.4 后置条件

- 在服务端工作空间创建稳定 `project_id` 和项目记录；客户端只建立本地音频关联与可清理缓存。
- 所有可识别文件均得到导入结果：已配对、仅音频、仅字幕、冲突、忽略或失败。
- 原始字幕内容和源文件元数据被只读保存。
- 波形、哈希、增强代理和 VAD 进入后台任务队列。
- 项目首页展示文件数、总音频时长、字幕段数和待处理异常。

### 3.1.5 界面及交互

#### 新建项目

| 元素 | 类型 | 必填 | 默认值 | 校验规则 | 操作反馈 |
| --- | --- | --- | --- | --- | --- |
| 项目名称 | 文本框 | 是 | 所选目录名 | 1 至 80 字符，项目内唯一 | 重名时建议追加日期 |
| 源目录 | 目录选择器 | 是 | 无 | 必须可读 | 扫描后显示文件摘要 |
| 服务端数据位置 | 服务端配置 | 否 | 服务启动时的数据目录 | 仅服务管理员配置；客户端不要求选择 | 显示服务端可用空间（如可用） |
| 默认语言 | 下拉框 | 是 | 简体中文 | V1.0 仅 zh-CN 完整支持 | 决定标点与文本规则 |
| 校对规范 | 下拉框 | 是 | 忠实逐字 | 忠实逐字 / 自定义 | 可进入项目设置细化 |
| 导入方式 | 单选 | 是 | 引用源文件 | 引用 / 复制到项目 | 复制方式显示空间需求 |

#### 配对确认页

| 列 | 内容与操作 |
| --- | --- |
| 规范化名称 | 去扩展名、Unicode NFKC、首尾去空白、连续空白折叠为一个空格后的名称 |
| 音频 | 文件名、格式、时长、大小、哈希状态 |
| 字幕 | 文件名、编码、段数、首末时间 |
| 结果 | 自动配对 / 仅音频 / 仅字幕 / 多候选冲突 / 格式错误 |
| 操作 | 更换配对、作为新文件导入、忽略、查看原路径 |

自动配对算法：

1. 分别扫描支持的音频和字幕扩展名。
2. 对不含扩展名的文件名做 Unicode NFKC 规范化。
3. 去除首尾空白，把任意连续空白折叠为一个半角空格。
4. 先按规范化名称完全相等匹配。

6. 导入后保存实际源文件名；导出来源引用默认使用字幕原文件名，而非规范化名。

## 3.2 音频播放、波形与非破坏性增强

### 3.2.1 描述

提供面向听写的低延迟播放能力：以“当前选中字幕段”为默认播放边界，支持精确跳转、段尾自动暂停、暂停回退、变速不变调、A-B 循环、波形缩放、音量增益和语音增强，并保证所有处理不改变源音频。普通播放不得自动串入相邻字幕段。

### 3.2.2 用户故事

- 作为主校对者，我希望暂停后再次播放时自动回退 1.5 秒，以便快速接回上下文。
- 作为主校对者，我希望每次播放只听当前要校对的一段，并在段尾自动暂停，以免下一段声音干扰当前文字判断。
- 作为主校对者，我希望点击字幕条目即可定位段首，行内按钮既能从该段开听，也能再次点击暂停在当前位置，以便右手用鼠标完成选段和播放控制。
- 作为主校对者，我希望把听不清的 4 秒范围持续循环，并在原音和增强音之间切换，以便辨认模糊词。
- 作为主校对者，我希望以 0.75 倍速度播放但保持音高，以便听清快速讲话。
- 作为复核者，我希望点击疑点后立即听到疑点前 2 秒至后 2 秒，以便不用手工找位置。

### 3.2.3 前置条件

| 类型 | 条件 |
| --- | --- |
| 数据 | 媒体已成功导入且源文件可访问 |
| 功能 | 原音播放不依赖波形、VAD 或增强任务完成 |
| 权限 | 用户有读取源音频权限 |

### 3.2.4 后置条件

- 播放位置实时写入会话状态，并至少每 5 秒持久化。
- 当前选中段作为普通播放的有效范围；段尾暂停后保留该段为当前工作段。
- 用户的速度、增益、增强预设和自动回退设置按项目/用户保存。
- 循环范围可临时使用，也可随疑点持久化。
- 播放本身不改变任何校对状态；只有显式确认才算人工审核。

#### 单段播放状态规则

| 触发动作 | 播放前处理 | 是否自动播放 | 段尾行为 |
| --- | --- | --- | --- |
| 点击字幕条目的非操作区域 | 若正在播放先暂停；选中被点击段；精确定位到 `start_ms` | 否 | 不适用 |
| 聚焦某条校对文本框 | 与点击该字幕条目相同；重复聚焦当前条目不应造成播放 | 否 | 不适用 |
| 点击未在播放的目标段行内“▶ 播放” | 选中该段并设为活动播放范围；若是换段、播放头已到段尾或位于该段外，定位到 `start_ms`；若同段暂停在段内，则按自动回退恢复且不得早于段首 | 是；按钮立即变为“⏸ 暂停” | 普通模式在 `end_ms` 自动暂停 |
| 点击正在播放的当前段行内“⏸ 暂停” | 立即暂停并保留当前播放位置；不得定位或重置到 `start_ms` | 否；按钮立即变为“▶ 播放” | 停在用户点击暂停时的位置 |
| 执行现有播放快捷命令 | 若播放头位于当前段内则从当前位置恢复，并按设置自动回退但不早于段首；若已到段尾或位于段外，则从段首开始 | 是 | 普通模式在 `end_ms` 自动暂停 |
| 播放时点击另一字幕条目 | 先暂停旧段，再切换选中段并定位新段 `start_ms` | 否 | 不允许旧段继续出声 |
| 开启当前段循环 | 保持当前段为播放范围 | 不改变当前播放/暂停状态 | 播放到 `end_ms` 后回到 `start_ms` 并继续；这是唯一自动回绕模式 |

边界约束：

- 普通播放的可听范围为闭开区间 `[start_ms, end_ms)`；检测到播放头达到或越过 `end_ms` 时，立即暂停并把界面位置稳定在段尾。
- 由于浏览器音频事件按帧调度，段尾动作允许不超过 100 ms 的实现误差，但误差期间不得可辨识地播放下一段内容。
- 行内按钮与播放快捷命令遵循同一套当前段状态规则：播放中触发即暂停且不跳转；同段暂停在段内时再次播放按自动回退恢复；换段、停在段尾或播放头位于段外时才从目标段段首开始。
- 行内按钮必须随当前状态显示“▶ 播放”或“⏸ 暂停”，其可访问名称同步为“播放”或“暂停”；按钮事件不得冒泡触发行定位。
- 播放按钮之后紧邻显示“⏪ 2s”和“⏩ 2s”两个行内复听按钮；可访问名称分别为“后退 2 秒”和“前进 2 秒”。按钮点击不自动播放；按钮所在段成为当前选中段，seek 结果受该段起止时间钳制。
- 普通播放过程中，后退、前进和自动回退都必须钳制在当前段内。
- 行内后退/前进按钮必须调用与 F7/F9 相同的 2 秒 seek 命令；点击按钮所在行先将该段设为当前选中段与活动播放范围。切换到另一行时暂停旧段并定位到目标段段首，再执行对应方向的 2 秒偏移；不因点击复听按钮自动开始播放。若目标行已经在播放，则保持播放状态并在该段范围内 seek；暂停时保持暂停。
- 行内后退/前进按钮的有效范围为 `[start_ms, end_ms]`，到边界时钳制，不得越过相邻段；按钮事件不得冒泡成普通条目定位或触发播放/暂停开关。
- 循环开关关闭后，下一次到达段尾恢复普通暂停规则。

增强预设的产品定义：

| 预设 | 目标 | 处理原则 |
| --- | --- | --- |
| 原音 | 保留原始听感 | 不做处理，只应用用户音量 |
| 语音清晰 | 提升讲话频段与响度一致性 | 温和高通、低通、压缩与响度归一；参数由音频预研确定 |
| 强降噪 | 稳定底噪明显的片段 | 降噪后限制增益，提示可能损失辅音 |
| 自定义 | 面向高级用户 | 可调降噪强度、语音频段、压缩和增益 |

约束：

- 所有增强输出均为可重建缓存，不写回源文件。
- 首次播放必须优先使用原音，不能等待增强代理。
- 增强算法不得生成或补写语音；界面明确写“辅助听辨，不代表原音事实”。
- 用户在增强模式下确认片段时，审计记录保存所用预设，便于复核。

## 3.3 逐字校对与时间轴编辑

### 3.3.1 描述

在原始识别层只读对照的基础上，按时间轴编辑逐字校对层，支持改字、断句、说话人、拆分、合并和确认，并维持稳定来源关系。

### 3.3.2 用户故事

- 作为主校对者，我希望当前字幕随播放高亮，并能直接输入修正，以便视线不离开正文。
- 作为主校对者，我希望按 Ctrl + Enter 确认当前段并自动进入下一段，以便连续处理。
- 作为主校对者，我希望已确认段的行内按钮可再次点击以撤销确认，以便发现问题时立即恢复编辑状态。
- 作为主校对者，我希望拖动左侧列表滚动条时滑块与鼠标同步，不被播放跟随抢回，以便快速到达远处字幕。
- 作为主校对者，我希望“播放/暂停、后退 2 秒、前进 2 秒、确认/取消确认、疑点、循环”六个行内按钮拥有一致的可见高度和垂直对齐，以便操作区稳定、易扫视。
- 作为主校对者，我希望在长字幕列表中连续输入时文字逐键立即出现，自动保存留在后台完成，以便保存保护不会打断校对节奏。
- 作为主校对者，我希望把被机器截断的一句话合并，同时保留原始两个 cue 的映射，以便修正断句但不丢证据。
- 作为复核者，我希望看到原始识别与校对稿的差异，以便了解人工改了什么。

#### 选中与播放规则

- 点击字幕段非操作区域：若旧段正在播放则先暂停；选中被点击段并把播放头精确移到其 `start_ms`，不自动播放。
- 聚焦某段校对文本框：执行与点击该字幕条目相同的选中和定位规则，不因获得编辑焦点而自动播放。
- 行内原“▶ 定位”按钮改为同一个播放/暂停开关：目标段未播放时显示“▶ 播放”，点击后自动选中并按当前段状态规则开始播放；目标段正在播放时显示“⏸ 暂停”，再次点击暂停在当前位置，绝不能重新跳到 `start_ms`。
- 同一段暂停在段内后再点“▶ 播放”，按自动回退恢复且不得早于段首；换到另一段、停在段尾或播放头位于目标段外时，才从目标段 `start_ms` 开始。
- 双击时间码：等价于操作该段行内播放/暂停开关。
- 普通播放只播放当前选中段，到 `end_ms` 自动暂停；不得默认继续下一段。
- 播放进入当前段时可同步高亮，但不得抢走校对文本框的输入焦点。
- Ctrl + Enter：保存并确认当前段，选择下一未校对段并精确定位其 `start_ms`，不自动播放。

#### 行内确认/撤销确认规则

- 未确认段显示“✓ 确认本段”；通过校验并点击后，状态改为“已确认”，按钮立即变为“↶ 取消确认”（可达名称同步），并将按钮所在段设为当前选中段与活动播放范围。若原先选中的是其他段，也必须选中被确认的这一段，绝不能错误前进到下一段。
- 已确认段再次点击同一行内按钮时，不再执行一次“确认”，而是撤销确认；有未解决疑点时回到“有疑点”，否则回到“校对中”。
- 撤销确认必须立即进入自动保存队列；重启应用后不得恢复为“已确认”。
- 行内确认或撤销确认后，选中目标均为按钮所在段；不得选中下一段。该操作不自动播放，不改变播放头或播放/暂停状态。
- `Ctrl+Enter` 仍是“确认当前段并前进”的连续校对命令，本次不改成撤销快捷键。

#### 行内操作按钮尺寸规则

- 同一字幕段的“播放/暂停”“后退 2 秒”“前进 2 秒”“确认本段/取消确认”“⚑ 疑点”“循环”六个按钮必须使用同一按钮盒模型：相同的可见高度、上下内边距、边框宽度、行高和垂直对齐。
- 在浏览器缩放 100%、125%、150% 和 200% 下，六个按钮的 `getBoundingClientRect().height` 最大值与最小值之差均不得超过 1 CSS px；按钮文字宽度可自适应，不要求六个按钮等宽。
- “⚑ 疑点”的类型菜单可通过浮层或 portal 定位，但触发按钮不得因额外包裹层改变 flex 拉伸结果、行高或基线；打开和关闭菜单不得改变按钮尺寸及字幕行高。
- “播放”切换为“暂停”、“确认本段”切换为“取消确认”时允许宽度随文字变化，但高度不得变化，也不得造成相邻按钮上下跳动。

#### 输入与自动保存响应规则

- 校对文本必须在输入事件或中文输入法一次组合提交后立即显示；自动持久化在后台按现有 500 ms 停顿防抖执行，不得让磁盘写入、保存状态提示或全量派生计算阻塞文字显示。
- 普通正文编辑只改变目标字幕段的文本和必要状态。单次键入不得让未修改的字幕行重渲染，不得因时间范围未变化而重新排序完整时间轴，也不得逐键重建仅在导出时才需要的全量预览。
- 自动保存继续按片段去重并保留最新内容；连续输入期间可以维持同一个“保存中”状态，不得为相同状态逐键广播全工作台更新。输入停止约 500 ms 后落盘，成功、失败和重试语义保持不变。
- 中文 IME 组合期间不得保存半个组合字；`compositionend` 后完整文字立即进入状态和保存队列。页面隐藏、返回项目或其他受保护导航前，仍须刷新待保存队列。
- 性能优化不得以关闭自动保存、只在失焦时保存、把文字显示延迟到防抖结束，或丢弃失败队列为代价。

#### 列表人工滚动优先规则

- 左侧字幕列表开启“跟随播放”时，只有在用户未主动滚动的情况下，才可以用程序滚动把当前段带入视口。
- 鼠标拖动原生纵向滚动条、点击滚动轨道、滚轮、触控板及键盘滚动均视为人工接管；首个人工滚动事件即暂停跟随。
- 人工接管后，即使音频继续播放、当前段继续变化，也不得执行 `scrollIntoView` 或其他程序滚动。
- 拖动滚动条期间，滑块和列表位置必须与鼠标连续同步，不得后退、跳回播放段或在松手后才追上。
- 只有用户显式点击“回到播放点”，或执行明确要求跟随目标段的定位/播放操作时，才可恢复跟随。

#### 拆分

- 默认以光标位置拆文字，以当前播放位置拆时间。
- 若播放位置不在该段内，使用段时间中点并要求确认。
- 新段继承说话人、段类型和来源映射；两个新段状态均为“校对中”。
- 原段进入历史，不物理删除；相关疑点按文字锚点和时间范围重新归属。

#### 合并

- 仅可合并同一文件中相邻段。
- 新范围取最早开始至最晚结束；文本以可配置分隔符合并，默认无空格。
- 说话人不同时要求选择保留、标记多人或取消。
- 任一原段有未解决疑点时，疑点保留并迁移。

#### 时间轴吸附

- 拖动边界默认吸附到 10 ms。
- 可吸附到相邻段边界、播放头和波形局部静音点。
- 按 Alt 暂时关闭吸附。
- 不允许用一次批量操作默默截断文字；批量偏移前展示影响预览。

## 3.4 疑点、上下文与术语表

### 3.4.1 描述

把“听不清、拿不准、需要查证”从临时记忆变成结构化任务。疑点可锚定文字范围与音频范围，自动带上上下文、候选写法、已尝试方法和处理结论；术语表帮助跨文件保持专名一致。

### 3.4.2 用户故事

- 作为主校对者，我希望用一个快捷键把当前词和音频范围加入疑点队列，以便不中断主流程。
- 作为用鼠标校对的主校对者，我希望点击左侧字幕行内“⚑ 疑点”后先选择真实疑点类型，以免每次都被错误记成“听不清”。
- 作为复核者，我希望打开疑点就自动循环其前后文，并看到其他文件中的相似用词，以便更快做判断。
- 作为成稿编辑者，我希望专名有统一标准写法和别名，以便避免同一术语在 66 小时材料里出现多种写法。
- 作为项目负责人，我希望任何“听不清”都有明确结论和责任状态，以便最终版不存在被遗忘的占位符。

### 3.4.3 前置条件

| 类型 | 条件 |
| --- | --- |
| 数据 | 疑点必须关联至少一个媒体时间范围或一个文本对象 |
| 权限 | 校对者可创建和编辑；复核动作需切换为复核者身份 |
| 功能 | 全局检索索引可异步建立；索引未完成不阻塞创建疑点 |

### 3.4.4 后置条件

- 疑点进入队列并影响相关片段和文件状态。
- 阻塞级疑点未解决时，项目不能通过最终质量闸门。
- 解决疑点后写入最终文字、依据和审计事件，相关片段回到“校对中”并需重新确认。
- 接受不可辨时插入项目统一占位符并保存签署信息。

### 3.4.5 界面及交互

#### 创建疑点

若用户先选中文字，则文字锚点为选区，音频范围取关联字幕段；若没有选区，则以播放头为中心取前 2 秒、后 2 秒，用户可在波形中调整。

##### 左侧工作区行内“⚑ 疑点”

1. 点击某条字幕的行内“⚑ 疑点”只打开紧邻该按钮的轻量类型选择层；此时不得写入疑点、不得增加未解决计数，也不得自动假定为“听不清”。
2. 选择层必须列出全部类型：听不清、同音词、专名、数字、断句、说话人、事实待查、时间轴；初始时无预选项。
3. 用户点击具体类型后，才为被点击的字幕段创建且只创建一条疑点；类型为用户所选值，行内快速创建的严重级别仍为“阻塞”、备注为空，随后关闭选择层。
4. 点击按钮以外区域、按 `Esc` 或再次点击同一“⚑ 疑点”均只取消选择，不创建记录。同一时间最多展开一个类型选择层。
5. 行内疑点按钮和类型选择操作不得冒泡为条目定位，不改变播放头，不自动播放。
6. 疑点面板的辅助提示固定显示为“行内‘⚑ 疑点’按钮会直接创建默认疑点；快捷键 Ctrl+? 同。”，不再展开“（听不清 / 阻塞）”类型与级别说明。本句是指定的界面文案，不覆盖第 1–5 条：行内按钮仍先打开类型选择层，未选择类型时不得创建；`Ctrl+?` 的既有快捷创建规则不变。

##### 右侧完整疑点表单

下表适用于右侧“为当前段新建疑点（表单）”的完整创建流程，不是左侧行内类型选择层的默认规则。V1.0.4 撤销 V1.0.3 对该表单“每次强制重置类型”的要求，恢复 V1.0.2 之前的表单行为。

| 元素 | 类型 | 必填 | 默认值 | 校验规则 | 反馈 |
| --- | --- | --- | --- | --- | --- |
| 疑点类型 | 下拉 | 是 | 听不清 | 听不清/同音词/专名/数字/断句/说话人/事实待查/时间轴 | 决定检查规则 |
| 严重级别 | 单选 | 是 | 阻塞 | 阻塞/警告 | 阻塞影响最终导出 |

| 文字范围 | 文本锚点 | 条件必填 | 当前选区 | 与段修订版本关联 | 段变化后自动重定位或报冲突 |

| 备注 | 多行文本 | 否 | 空 | 最多 2,000 字 | 自动保存 |
| 指派给 | 下拉 | 否 | 未指派 | V1.0 为动作身份 | V1.1 对应真实用户 |

#### 疑点详情

固定展示：

- 疑点前后至少三个字幕段。
- 原始识别、当前校对文本及差异。
- 一键 A-B 循环、原音/增强切换和速度设置。
- 全项目相同词、同音候选和相邻高频词的搜索结果。
- 术语表命中、别名、证据链接及使用次数。
- 已尝试方法复选：原音、减速、增益、语音清晰、强降噪、查上下文、查术语、交叉文件。
- 操作：采用候选、直接填写、暂缓、接受不可辨、关闭为非问题。

#### 接受不可辨规则

**[待确认 C3]** 建议占位符统一为“[听不清 01:23:45.678]”，并要求至少勾选三种已尝试方法后才能签署。成稿层默认不直接展示时间，而以“[原音不清]”或编辑性删节处理；证据层永远保留精确时间。

接受不可辨不是“解决为确定文本”，其状态和统计必须单独展示。若后续得到更清晰音源，可重新开启。

## 3.5 成稿编辑与来源映射

### 3.5.1 描述

把已确认的逐字校对片段整理为可读书稿，同时维持段落到一个或多个原音范围的显式映射。成稿编辑不反向覆盖逐字稿。

### 3.5.2 用户故事

- 作为成稿编辑者，我希望把连续的已确认片段加入一个书稿段落，并在右侧改写，以便去除口语但保留证据。
- 作为复核者，我希望点击成稿段落即可依次播放其全部来源，以便检查是否改变原意。
- 作为项目负责人，我希望任何无来源的成稿文字被明确标记，以便避免模型或编辑无意添加事实。
- 作为现有书稿维护者，我希望导出“标题 + 章节 + 来源 + 正文”的 Markdown，以便进入当前流水线。

### 3.5.3 前置条件

| 类型 | 条件 |
| --- | --- |
| 数据 | 默认只能从“已确认”或“接受不可辨”的校对片段建立来源 |
| 配置 | 项目至少有一个章节；默认创建“未分类” |
| 权限 | 当前动作身份具有成稿编辑权限 |

### 3.5.4 后置条件

- 成稿段落拥有正文、章节、顺序、状态和来源范围。
- 校对片段后续改变时，引用它的成稿段落自动变成“来源已变化，待复核”。
- 成稿段落可导出为纯文本或带来源 Markdown。
- 成稿与逐字稿分别计数和验收。

### 3.5.5 界面及交互

#### 双栏编辑

左栏是可筛选的已确认校对片段，右栏是章节化成稿。用户可：

1. 多选连续或非连续片段，点击“加入成稿”。
2. 选择新建段落、附加到当前段落或作为独立引用。
3. 在右栏编辑标题与正文；底部显示来源 chips。
4. 点击某个来源 chip，左栏定位并从该范围播放。
5. 拖动来源 chip 调整播放顺序，但不改变原时间。
6. 查看“成稿 ↔ 校对稿”语义差异提示；提示只辅助，不自动否决。

| --- | --- | --- | --- | --- | --- |
| 章节 | 树选择 | 是 | 未分类 | 必须为启用章节 | 变更后目录实时更新 |

#### 来源范围压缩规则

- 同一文件中相邻且间隔不超过 500 ms 的来源可在展示层合并。

- 跨文件来源不能压缩为单一区间。
- 成稿删除一段文字不会自动删除来源；系统提示检查冗余来源。
- 添加与来源无明显对应的新陈述时，编辑器给出“可能无来源”警告，用户需删除、改为编辑注或补充来源。

## 3.6 语音覆盖、质量检查与完成闸门

### 3.6.1 描述

用音频时长、语音活动候选、字幕时间轴、人工状态、疑点和来源映射联合判断完成度，避免“字幕改到最后一行”但仍漏音、留疑或失去出处。

### 3.6.2 用户故事

- 作为项目负责人，我希望看到哪些有声区间还没有文字，以便发现机器漏转。
- 作为主校对者，我希望质量问题能直接跳到音频和对应段，而不是只给一份抽象报告。
- 作为项目负责人，我希望系统只有在所有阻塞项清零时才允许签署最终版，以便“完成”有一致标准。
- 作为复核者，我希望区分“未解决疑点”和“已接受不可辨”，以便不把诚实保留的问题误当遗漏。

### 3.6.3 前置条件

| 类型 | 条件 |
| --- | --- |
| 数据 | 音频媒体信息已读取 |
| 分析 | VAD 可异步运行；未完成时对应覆盖检查标为“未知”，不能视为通过 |
| 权限 | 所有人可运行检查；只有项目负责人可签署完成 |

### 3.6.4 后置条件

- 生成项目、文件和具体对象三级质量报告。
- 每个问题具有规则 ID、级别、位置、修复入口和状态。
- 质量闸门通过后产生不可变签署记录及所依据的项目版本。
- 签署后的任意内容修改立即使签署失效。

### 3.6.5 界面及交互

#### 覆盖时间轴

同一时间轴叠加四条轨：

1. 音频全长。
2. VAD 检出的语音候选。
3. 有校对文字映射的范围。
4. 已人工确认或接受不可辨的范围。

区间分类：

| 分类 | 条件 | 默认处理 |
| --- | --- | --- |
| 已覆盖 | 有效语音与已确认片段重叠达到阈值 | 通过 |
| 有声无字 | VAD 为语音，但没有任何语音片段覆盖 | 阻塞候选，必须试听 |
| 有字无声 | 有语音文本，但 VAD 未检测到语音 | 警告，可能是 VAD 漏检或时间轴偏移 |
| 未人工确认 | 有文字，但片段状态不是已确认/接受不可辨 | 阻塞 |
| 非语音 | 用户确认音乐、静音或环境声 | 不要求逐字文本，但需类型标签 |
| VAD 未完成 | 后台分析未结束或失败 | 状态未知，最终闸门不通过 |

VAD 只产生候选，不直接删除、添加或确认文字。对于“有声无字”，用户必须选择：

- 补建语音片段并校对；
- 标记为音乐；
- 标记为环境声；
- 标记为不需转写的无意义人声，并写备注；
- 判定为 VAD 误报。

#### 质量规则

| 规则 ID | 检查 | 级别 | 通过条件 |

- 疑点进度独立显示，不与校对段数混成一个百分比。
- 成稿进度以“已批准且来源未变化的段落”计算。

## 3.8 自动保存、版本历史与崩溃恢复

### 3.8.1 描述

确保数周到数月的校稿不会因应用退出、误操作、磁盘问题或错误批量修改而丢失，并允许查看差异、建立里程碑和恢复历史版本。

### 3.8.2 用户故事

- 作为主校对者，我希望输入后无需手动保存，以便专注听写。
- 作为项目负责人，我希望批量替换前自动创建快照，以便发现错误后整体恢复。
- 作为成稿编辑者，我希望比较任意两个成稿版本，以便知道复核修改了什么。
- 作为用户，我希望应用崩溃后回到刚才的文件和位置，以便最大限度减少重复工作。

### 3.8.3 前置条件

| 类型 | 条件 |
| --- | --- |
| 存储 | 服务端项目数据目录可写；客户端可暂存未提交草稿 |
| 数据库 | 支持事务和写前日志或同等级别持久性机制 |
| 配置 | 用户未显式进入只读快照模式 |

### 3.8.4 后置条件

- 普通编辑在停止输入 500 ms 后持久化，最长 5 秒强制提交。
- 每个逻辑操作生成审计事件；复杂操作原子提交。
- 高风险操作前创建自动快照。
- 服务重启后能恢复到最近持久化版本和工作位置；客户端刷新或换设备后从服务端恢复同一状态。
- 服务不可用时未提交操作保留在客户端队列，恢复后按原 `expectedRevision` 重试；不静默写入另一份本地数据库。

## 3.9 导出与现有书稿流水线衔接

### 3.9.1 描述

在质量预检通过后，把逐字校对稿、成稿、问题清单和项目证据导出为开放格式。默认永不覆盖源文件，并为现有“环境画卷”Markdown 流水线生成可直接审阅的来源格式。

### 3.9.2 用户故事

- 作为主校对者，我希望导出修正后的 SRT 并保留毫秒时间码，以便其他播放器仍可使用。
- 作为成稿编辑者，我希望导出 Markdown，每个小节都有标题、章节和来源范围，以便并入现有书稿。
- 作为项目负责人，我希望导出时附带质量报告、源哈希和版本号，以便知道这份“最终稿”基于什么。
- 作为用户，我希望导出失败时原有文件不被截断，以便避免损坏成果。

# 四、非功能需求（注意事项）

## 4.1 安全、隐私与合规

| 需求 | 说明 | 验收方式 |
| --- | --- | --- |
| 服务可控与最小外联 | V1.0 服务运行在用户控制的机器/局域网；除同一服务 API 外不向第三方上传项目内容；若服务不可用，客户端保留草稿但不冒充已同步 | 断开外部网络但保留本地服务时完成校对；停止服务时验证失败队列和恢复；抓包确认无第三方项目数据外发 |
| 最小外联 | 可选更新检查、二次 ASR 或错误上报必须单独开关并说明发送内容 | 抓包确认默认零项目数据外发 |
| 明示授权 | 发送音频片段给外部服务前，展示范围、服务方、用途、保留策略和预计费用 | 未确认时请求不得发出 |
| 源文件只读 | 应用不写回、不重命名、不删除源音频和源字幕 | 文件哈希与修改时间不变 |
| 服务端数据保护 | 服务端项目数据库权限仅限服务进程/管理员；局域网部署建议绑定受控网卡并可选 HTTPS/整盘加密 | 检查服务目录权限、备份恢复和网络暴露面 |
| 日志脱敏 | 默认不记录正文、完整本地路径或音频内容；错误日志使用对象 ID | 审阅日志样本 |
| 审计可追溯 | 确认、接受不可辨、批量替换、恢复、签署和导出必须记录 | 随机抽取操作核对 |
| 删除可恢复 | 删除编辑对象进入回收站；源文件从不由应用删除 | 30 天内恢复测试 |
| 版权提示 | 用户导出或调用外部模型时确认其有权处理相关录音 | 首次操作提示 |

若未来加入多人服务端，需要另行完成身份认证、RBAC、传输加密、静态加密、租户隔离、数据驻留和删除请求设计；不以本地权限模型直接外推。

#### 服务端项目空间与跨设备边界（V1.1.0 架构基线）

- 同一服务端工作空间是项目、校对文本、确认状态、疑点、播放位置、更新时间和 revision 的唯一事实源；客户端不因浏览器、设备或 origin 不同而拥有另一份项目历史。
- `0.0.0.0` 只改变监听范围，让局域网设备访问同一服务；它本身不是同步机制，必须由 `/api` 持久化接口和服务端数据库提供共享。
- 浏览器 IndexedDB 只作为缓存或旧版本迁移来源。旧数据迁移必须幂等：服务端缺失时创建，服务端已存在时不覆盖；成功前不删除本地数据，失败可重试；不上传 MP3 正文。
- 服务端写入必须携带 `revision`、`If-Match` 或等价的 `expectedRevision`。版本不一致返回 HTTP 409；客户端保留本地草稿并让用户刷新/比较/重试，禁止最后写入静默覆盖。
- 服务不可用时不切换到另一份本地项目历史冒充已同步数据；当前编辑可留在内存和失败队列，服务恢复后再提交。
- 服务端默认只保存结构化项目数据和原始 SRT。每台设备仍需选择或重新定位本地 MP3，并用源哈希/时长校验；是否托管音频是后续单独决策。

## 4.2 统计需求（本地埋点）

为保护内容隐私，V1.0 的产品分析事件默认只存本地聚合数据，不包含正文、候选文字、文件路径或音频。用户可在设置中导出匿名统计供产品评估。

| 事件名 | 触发时机 | 属性 | 用途 |
| --- | --- | --- | --- |
| project_created | 项目创建成功 | project_id_hash, file_count, audio_hours_bucket | 了解项目规模 |
| import_completed | 一次导入完成 | paired, audio_only, subtitle_only, conflict, failed, duration_ms | 衡量导入质量 |

### 4.4.4 服务端 API 与并发契约

服务端 API 是所有客户端的共同入口，至少提供以下资源（具体路由可兼容实现，但语义不可省略）：

| 方法 | 路径 | 语义 |
| --- | --- | --- |
| GET | `/api/projects` | 返回服务端工作空间内全部项目摘要，按 `updated_at` 倒序 |
| POST | `/api/projects` | 创建项目；重复迁移请求以稳定 `project_id`/幂等键返回既有项目 |
| GET | `/api/projects/:projectId` | 返回项目元数据、revision、媒体、SRT、segments、issues、playback |
| PATCH | `/api/projects/:projectId/playback` | 更新播放位置/当前段，携带 `expectedRevision` |
| PATCH | `/api/projects/:projectId/segments/:segmentId` | 更新校对文本、时间轴、确认状态，携带 `expectedRevision` |
| PUT/DELETE | `/api/projects/:projectId/issues/:issueId` | 创建、更新或删除疑点，携带 `expectedRevision` |
| POST | `/api/projects/:projectId/migrate` | 幂等迁移旧客户端项目；服务端已有版本不被本地旧稿覆盖 |
| GET | `/api/projects/:projectId/audit-events` | 只读审计事件查询（V1.1.1）：按 id 升序稳定分页，支持 `afterId` 与 `limit`；不提供任何修改/删除审计事件的 API（§4.4.6） |

写入约定：

1. 成功写入以事务方式更新数据、`revision` 和 `updated_at`，返回新 revision 及受影响对象。精确口径（V1.1.2）：首次创建 revision=1（不携带 `expectedRevision`）；“成功写入”指对既有项目产生实际状态变化的写操作——已定义的幂等/no-op 例外（幂等重复创建/迁移返回既有 revision、与当前持久值完全相同的 segment/issue 写入返回当前 revision、对不存在对象的幂等删除）不增长 revision，见 §4.4.6 一.2。
2. 缺少或不匹配 `expectedRevision` 返回 `409 Conflict`，响应包含服务端当前 revision 和可重新读取的对象摘要；不得返回 2xx 假装已保存。
3. 客户端可发送 `If-Match: "<revision>"`，服务端应与 `expectedRevision` 等价处理。
4. 所有写入接口必须校验 project/segment/issue 所属关系、字段范围和请求体大小；未知字段不得静默落库。
5. 服务重启后数据和 revision 不丢失；数据库文件、WAL 和备份目录不由浏览器访问。
6. 客户端写入请求应携带 `X-TingProof-Client-Id`（持久非实名客户端实例 ID）与 `X-TingProof-Source`（来源标识）请求头；服务端严格校验长度与字符集并记入审计事件，缺失时诚实回退 `unknown` / `api`（V1.1.1，见 §4.4.6）。

### 4.4.6 ground-truth 审计契约（V1.1.1，当前实现范围）

本节描述的能力**已经实现并通过自动化测试**，不是未来规划。目的：把一次真实的人工标注过程（听、改、确认、存疑、解决、删除）完整还原为可机读的时间线，作为马上进行的人工标注与后续机器预筛评估的 ground truth。

**一、事件结构与产生时机**

1. 每次成功的服务端写入在同一事务内追加一条审计事件；数据写入、revision 增长与审计写入原子提交，任何一方失败则全部回滚。
2. 失败写入、校验拒绝（400）与版本冲突（409）**不产生**审计事件；对不存在对象的幂等删除（如删除已不存在的疑点）也不产生事件、不增长 revision。**语义 no-op（V1.1.2）**：与当前持久值完全相同的 segment/issue 写入、以及分阶段补丁相互抵消后净状态无变化的 media 更新（均基于 canonical 前后值判断，`changedFields` 为空）同样是成功但无变化的请求——不写对象、不增长 revision、不产生审计事件，返回当前对象与当前 revision。media 的 `changedFields` 在全部补丁应用并 canonical 后一次性基于最终前后值计算，按白名单键序稳定排列且绝不重复。
3. 每条事件至少包含：单调递增 `id`、`projectId`、写入后 `revision`、`action`、`objectType`、`objectId`、`timestamp`、`clientId`、`source`、`before`、`after`、`changedFields`、`metadata`。`before`/`after` 是结构化 JSON 对象或 null，不得以不可解析字符串暴露给 API 消费者。
4. 动作词表与 before/after 语义见 §3.8.8：疑点区分 `create_issue / update_issue / resolve_issue / reopen_issue / delete_issue`（删除前完整 IssueRecord 保存在 `before`，`after` 为 null；解决与重开保存前后状态）；字幕段按实际前后差异区分 `edit_segment_text / confirm_segment / unconfirm_segment / update_segment_timing / update_segment`，一次请求同时改变多类字段时用 `update_segment` 且 `changedFields` 必须准确；`originalText` 永不可改。**精确语义（V1.1.2）**：疑点写接口返回值与审计 `after` 一律取自数据库最终行（canonical——请求省略 `resolvedAt` 时，持久行、返回值、审计 after 三处一致为 null）；已有疑点的 `createdAt` 创建后不可变，更新请求与其不一致时 400 回滚（无写入、无事件、无 revision 变化）；`issues.issue_id` 为全局主键，写入前必须校验既有同名疑点的项目归属——跨项目冲突返回 404，双方数据、revision 与审计零污染；导入/迁移新项目时 issueId 与既有项目碰撞、或同一载荷内重复 issueId，都使整个创建事务回滚（400，不 last-write-wins）；`create_project` 快照的 `segmentCount/issueCount` 取实际插入值，与主表 canonical 数据一致。
5. 事件轻量边界：约每 5 秒一次的 `update_playback` 事件保持轻量（不复制大对象，摘要写入 metadata）；项目创建、media 更新等低频事件按合理方式补充快照。

**二、客户端来源（诚实边界）**

1. 当前没有账号体系，不伪造真人身份。前端 `RemoteProjectRepository` 为每个请求携带一个**持久但非实名**的 client instance ID（浏览器 localStorage 保存，形如 `ci-<uuid>`）与明确 source（`web`）。
2. `clientId` 可以区分客户端实例（不同浏览器/设备/无痕窗口通常不同），但**不代表经过认证的人**；同一个人可用多个实例，一个实例也可能被多人使用。审计消费方不得把 clientId 当作署名。
3. 服务端对两个请求头做严格校验（长度与 `[A-Za-z0-9_-]` 字符集，非法返回 400）并原样记录；缺失时使用诚实的 `unknown`（clientId）/`api`（source）回退，不编造来源。

**三、只读查询 API**

1. `GET /api/projects/:projectId/audit-events` 返回该项目全部审计事件，按 `id` 升序稳定分页。
2. 查询参数：`afterId`（返回 id 严格大于该值的事件，默认 0，非负整数）与 `limit`（1–500，默认 100，超上限或非法值返回 400）。响应包含 `events`、`pagination.afterId / nextAfterId / limit / hasMore`，调用方以 `nextAfterId` 续页，遍历过程无重复、无遗漏。
3. 项目不存在返回 404。**不提供任何修改或删除审计事件的 API**；审计日志只追加，不更新。
4. **损坏即失败（V1.1.2）**：查询遇到非 SQL NULL 且无法解析、或类型不符合字段预期（对象字段收到数组/标量、数组字段收到非字符串数组）的 JSON 时必须明确失败并暴露数据损坏（含事件 id 与字段名），不得静默当作 null 伪装成“历史未记录”；SQL NULL 仍诚实表示迁移前未记录。
5. 本轮不要求审计 UI；接口与数据库结构即为 ground-truth 导出通道。

**四、存储与迁移（SQLite 实现口径）**

1. 新建数据库直接创建最新 schema（`audit_events` 含 `client_id / source / before_json / after_json / changed_fields_json / metadata_json` 列与 `(project_id, id)` 索引）。
2. 旧数据库（V1.1.1 之前，仅有旧 7 列——`id、project_id、revision、action、object_type、object_id、at`——的 `audit_events`）在打开时**原地、幂等、无损**迁移：以 `ALTER TABLE ADD COLUMN` 补齐新增 6 列（富表共 13 列），绝不 drop/recreate 任何表、绝不丢弃既有 `audit_events` 行；旧行在新列上保持 null 并在 API 中原样返回。
3. 显式 schema version：使用 SQLite `PRAGMA user_version` 记录（构造 store 时读取与升级，可被自动化测试断言）；迁移可重复执行（重复启动幂等）。**版本只进不退（V1.1.2）**：打开数据库先读版本，高于当前程序支持的 `SCHEMA_VERSION` 时明确拒绝——保持版本号、表结构和数据完全不变（不降级、不先执行当前 schema DDL），报错提示升级程序；只有低于或等于当前版本才执行迁移。**构造失败释放句柄（V1.1.2）**：数据库成功打开之后的任何初始化异常（读取版本、PRAGMA/SCHEMA/迁移、语句预编译等）都以 best-effort 方式关闭数据库句柄后原样重抛，不泄漏文件描述符；成功构造行为不变。
4. 事件随项目长期保留（§4.4.5）；项目被完整删除后其审计行仍留在数据库文件中（历史不清洗），但对应查询 API 返回 404。

## 5.1 验收标准与测试要点

### 5.1.1 端到端验收场景

以真实文件“青创 一   1   7月25日 上午9点10分.mp3”及其单空格 SRT 为基准：

1. 新建项目并选择“books/transcripts/环境画卷”目录。

3. 首个文件在全量波形/VAD 完成前可开始播放和编辑。
4. 用户点击任一字幕条目，应用暂停旧播放、选中该条并精确定位段首，但不自动播放。
5. 用户点击该条行内“▶ 播放”，应用从段首开始且按钮变为“⏸ 暂停”；播放中再次点击同一按钮，应用暂停在当前位置且不跳回段首；再次播放按自动回退恢复且不早于段首。普通模式最终只播放这一段并在段尾自动暂停，下一段没有被播放。
6. 用户点击左侧某条字幕的行内“⚑ 疑点”：只出现未预选的类型选择层，未解决数不变；点击“专名”后才创建一条类型为“专名”的阻塞疑点。再次打开并按 `Esc` 或点击外部，不得新增“听不清”或任何其他记录。
7. 当前选中 A 段时，用户点击 B 段的“✓ 确认本段”，B 变为“已确认”、按钮变为“↶ 取消确认”，且当前选中段切换为 B，不得跳到 B 的下一段；再次点击后 B 恢复为“校对中”（有未解决疑点时为“有疑点”），仍选中 B，重启后保持撤销结果。只有 `Ctrl+Enter` 才确认后前进。
8. 播放继续进入新字幕段时，用户用鼠标拖动左侧列表纵向滚动条；列表立即停止自动跟随，滑块持续位于鼠标处，不跳回当前播放段。点击“回到播放点”后才恢复自动跟随。
9. 在同一真实文件的 1,676 段列表中，六个行内操作按钮保持同高；用户连续输入至少 100 个字符时文字逐键立即出现，未修改行不重渲染，停止约 500 ms 后保存完成，刷新后文本完整一致。
10. 疑点面板辅助提示不再显示“（听不清 / 阻塞）”；底部工具栏不再显示播放/暂停、后退 2 秒、前进 2 秒按钮及“选中策略”文字，同时行内播放、快捷键命令、时间轴、时间显示、速度、自动回退、循环和“回到播放点”仍可用。
11. 用户定位至 00:20:08.780，修改跨段断句，建立一个专名疑点。
12. 用户用 0.8×、+6 dB、A-B 循环和语音清晰模式听辨，并记录处理结论。
13. 用户完成一个字幕段确认；重启应用后，文本、状态、播放位置和设置全部恢复。
14. 用户把已确认来源加入成稿，编辑为书面段落，并一键回放来源。
15. 质量中心发现文件末尾音频与字幕末尾的差异，要求人工分类。
16. 所有阻塞项清零后签署完成，导出 SRT、Markdown、JSON 和质量报告。
17. SRT 可被应用重新导入且时间与文本一致；Markdown 来源格式符合现有书稿规范；源 MP3 和源 SRT 的哈希不变。

| AC-062 | 审计只读查询 API | `GET /api/projects/:projectId/audit-events` 按 id 升序返回事件；`afterId` 与 `limit` 分页无重复无遗漏；limit 有上限且非法值（0、超上限、非整数、非数字）返回 400；项目不存在返回 404；非 GET 方法被拒绝；不存在任何修改/删除审计事件的 API；查询遇到非 SQL NULL 且无法解析或类型不符的 JSON 时明确失败并暴露数据损坏（含事件 id 与字段），SQL NULL 旧行仍诚实返回 null | P0 |
| AC-063 | 失败不产生事件 | 409 版本冲突、400 校验拒绝与失败写入均不产生审计事件、不增长 revision；成功写入的数据变更、revision 增长与审计写入在同一事务内原子提交；成功但无变化的幂等请求（segment/issue 与当前持久值完全相同、media 分阶段补丁净状态无变化）不写对象、不增长 revision、不产生审计事件，返回当前对象与当前 revision；changedFields 基于最终前后值一次性计算，顺序稳定且绝不重复 | P0 |
| AC-064 | 旧库原地无损迁移 | 用真实旧 schema 数据库构造 store 后：迁移原地进行（不 drop/recreate 表）、既有 audit_events 行全部保留且可读（新列为 null）、项目/片段/疑点数据不变、重复启动幂等、schema version 可被测试断言；新库直接为最新 schema；高于当前程序版本的数据库被拒绝打开——版本号、表结构与数据保持不变（不降级、不执行 DDL）；构造期任何初始化异常（含不兼容 schema 导致的语句预编译失败）均释放数据库句柄后原样重抛，不泄漏文件描述符 | P0 |
| AC-065 | 重启后审计完整 | 服务重启后全部审计事件保留；以 afterId/limit 分页遍历同一项目事件，结果与重启前一致，无重复、无遗漏 | P0 |

### 5.1.3 文稿质量抽检

自动规则不能替代人工内容质量。最终签署前按文件执行抽检：

| 抽检层级 | 建议抽样 | 检查内容 | 不通过处理 |
| --- | --- | --- | --- |
| 逐字稿 | 每文件随机 3 段，每段 60 秒；另抽所有接受不可辨 | 漏字、错词、否定、数字、专名、时间范围 | 发现严重错误则扩大抽样；达到阈值时退回整文件 |
| 成稿 | 每章节至少 3 段，含跨来源段落 | 是否改变原意、是否新增事实、来源是否完整 | 段落退回；系统性问题退回章节 |
| 覆盖 | 每文件开头、末尾和 3 个 VAD 边界 | 是否把讲话误标为非语音 | 补建文字并重跑检查 |
| 导出 | 每种格式至少打开并回读一次 | 编码、时间、标题、来源、特殊字符 | 修复导出器后重新生成 |

严重内容错误定义：改变否定、数量、主体、因果、专名或核心观点。抽检阈值 **[待确认 C7]**；建议任何严重错误即退回相关文件，普通错字率超过千分之一时扩大至双倍样本。

## 5.2 发布准入标准

V1.0 发布必须同时满足：

1. AC-001 至 AC-065 中所有 P0 用例通过。
2. 使用至少三份真实音频完成生产试用：一份清晰、一份一般、一份最困难。
3. 连续 4 小时工作会话无崩溃、无音文漂移、无无法恢复的保存错误。
4. 真实项目 SRT 导出往返误差为 0 ms。
5. 对当前 21 份音频执行覆盖检查，能明确显示“各文件音频总长减去最后一条字幕结束时间”的合计差异 00:07:08.606；不得把这段差异自动等同为语音。
6. 源文件在导入、编辑、质量检查和导出后哈希不变。
7. 隐私测试确认默认无项目内容出网。
8. 至少完成一次从旧版本项目数据库升级与回滚演练。
9. 阻塞级安全、数据丢失和导出损坏缺陷为 0。
10. 两个独立客户端访问同一服务完成共享验收：项目列表、文本、确认状态、疑点、播放位置和 revision 一致；服务重启后仍一致；旧客户端并发写入收到 409 而不覆盖。

## 5.5 设计决策记录

| 决策 | 选择 | 未选择方案 | 原因 |
| --- | --- | --- | --- |

| 文稿模型 | 原始识别 + 逐字校对 + 成稿三层 | 单文本直接改到底 | 准确性与可读性目标不同，单层会丢证据 |

## 5.6 交接摘要

1. V1.0 是以服务端项目空间为事实源、可由多个设备访问的长音频校稿工具，核心不是重新转写，而是让人工校对可操作、可恢复、可验收。
2. 数据模型必须分为只读原始识别、逐字校对和成稿三层，并以毫秒时间范围互相映射。
3. P0 主链路为：批量配对 → 播放增强 → 逐段确认 → 疑点复核 → 成稿映射 → 覆盖 QA → 签署 → 导出。
4. 真实验收规模为 21 份音频、66:08:49.916、约 1.77 GiB、24,671 个 SRT cue。
5. 质量中心必须处理音频与字幕末尾合计 00:07:08.606 的差异，并用 VAD + 人工裁决查找其他潜在漏转。
6. V0.1 先以一份 3 小时以上真实文件做纵向样机；V0.5 用三份不同难度音频试产；V1.0 才跑全量。
7. 开发启动前优先确认 C2（成稿范围）、C3/C4（不可辨政策）、C6（平台顺序）；跨设备共享已按 C8 纳入当前架构。
8. 本轮试用暴露两个独立问题：项目入口只展示 `projects[0]` 导致第二个项目不可见，以及把浏览器本地存储误当成跨设备事实源；前者由服务端多项目历史修复，后者由服务端持久化、迁移和版本保护解决。
9. V1.1.1/V1.1.2 已实现 ground-truth 富审计契约（§4.4.6，AC-058 至 AC-065）：审计事件可还原人工标注全过程（含疑点删除前快照与字幕段动作分类），审计查询 API 只读分页；语义 no-op 不产生事件、createdAt 不可变、issue_id 全局隔离、schema 版本只进不退、损坏 JSON 明确失败；clientId 非实名，账号体系后置时需另行升级署名语义。
