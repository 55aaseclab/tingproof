## 已知且无需再次确认

- 当前真实语料位于 books/transcripts/环境画卷。
- 有 21 份 MP3，音频合计 66:08:49.916，约 1.77 GiB。
- 有 21 份 SRT，共 24,671 个字幕段。
- MP3 与 SRT 文件名存在连续空格差异，自动配对必须处理。
- 现有字幕包含水印、错词、跨段断句、标点不统一和潜在漏转。
- SRT 账本末尾合计比原音总长短 00:07:08.606；这只是已知尾差，不代表差异全部都是讲话，也不排除中间还有漏转。
- 用户要人工校对，软件的职责是提高操作效率并保证过程可验收，不能把 AI 候选当最终事实。
- 普通播放一次只播放当前选中的校对段，到该段 `end_ms` 自动暂停；不得串入下一段。只有显式开启当前段循环时，才在段尾回到段首继续。
- 点击字幕条目非操作区域或聚焦该条文本框，会先暂停旧播放、选中该段并精确定位到 `start_ms`，但不自动播放。
- 行内原“定位”按钮改为同一个播放/暂停开关：目标段未播放时显示“▶ 播放”，首次点击自动选中并从段首播放；目标段正在播放时显示“⏸ 暂停”，再次点击必须暂停在当前位置，不能重跳段首。
- 同一段暂停在段内后再次播放，按自动回退恢复且不得早于段首；换段、位于段尾或段外时再播放，才从目标段段首开始。
- 行内按钮的可见文案和可访问名称必须同步反映“播放/暂停”状态；按钮点击不得冒泡成条目定位。
- 左侧字幕工作区的行内“⚑ 疑点”按钮不得默认直接创建“听不清”；点击后先显示无预选的八种类型，用户点选具体类型后才创建。
- 点击行内“确认本段”或“取消确认”后，当前选中目标必须是按钮所在段，不能错误选中下一段；操作不自动播放、不改变播放头。只有 `Ctrl+Enter` 才确认并前进。
- 左侧列表的鼠标滚动条拖动、滚轮、触控板和键盘滚动都优先于播放跟随；人工接管后不得被 `scrollIntoView` 抢回，只能显式恢复跟随。
- 左侧每条字幕的“播放/暂停”“确认本段/取消确认”“⚑ 疑点”“循环”四个行内按钮必须同高并垂直对齐；各按钮宽度可随文案自适应，疑点菜单的定位容器不得改变按钮高度。
- 自动保存继续采用约 500 ms 防抖且不得关闭；校对文字必须逐键立即显示，普通正文编辑只使当前字幕行因文本变化重渲染，不得逐键重排完整时间轴、重建完整导出预览或重复广播相同“保存中”状态。中文输入法、页面隐藏和受保护导航的防丢规则保持不变。
- PRD V1.0.3 对右侧完整疑点表单的修改源于对问题位置的误解，已由 V1.0.4 废止；真正需要修改的是左侧行内“⚑ 疑点”。
- 快捷键重设计不进入本轮逐段播放实现；在跨浏览器与桌面端方案定稿前，现有默认键位保持不变。

## 必须确认（影响架构或 V1.0 开发）

### 1. V1.0 是否确定为“本地桌面应用，Linux 首发”？

- 对应标记：**[假设 A1]**、**[待确认 C6]**
- 默认建议：采用本地优先桌面应用；首发支持当前工作环境 Linux x86_64，项目数据格式保持跨平台，随后补 macOS 和 Windows。
- 推荐理由：音频总量大、单文件长、需要可靠访问本地文件、全局快捷键、后台解码和隐私隔离；纯网页方案会显著增加文件权限、缓存和浏览器生命周期风险。
- 可选决策：
  - 接受建议：Linux 首发，跨平台架构。
  - 三平台同时首发：开发和测试成本更高，排期需增加。
  - 改为浏览器应用：需重写文件访问、缓存、崩溃恢复和性能目标。
- 影响范围：技术选型、安装包、自动更新、媒体解码、文件 API、测试矩阵。
- 不确认的阻塞：阻塞客户端架构和 V0.1 开发。
- 建议拍板：**接受默认建议。**

### 2. V1.0 是否必须同时交付“逐字校对稿”和“可读成稿”？

- 对应标记：**[假设 A2]**、**[待确认 C2]**
- 默认建议：两层都做，原始识别层只读、逐字校对层忠实原音、成稿层负责去口语和章节化。
- 推荐理由：用户的目标是“完美文稿”，而不仅是修正字幕；若只做一层，编辑者会在“忠实原话”和“行文流畅”之间反复覆盖，证据链容易丢失。
- 可选决策：
  - 接受建议：V1.0 包含三层模型与成稿编辑。
  - V1.0 只做逐字稿：可缩短首版范围，但无法在软件内闭环产出书稿。
  - 成稿另用现有 Markdown 编辑器：听校只导出逐字稿和来源数据。
- 影响范围：数据库模型、工作台、质量规则、导出格式、V1.0 排期。
- 不确认的阻塞：阻塞核心数据模型冻结；后改成本高。
- 建议拍板：**保留成稿为 P0，但 V0.1 样机先验证逐字校对主链路。**

### 3. V1.0 是否按“单人使用，多种动作身份留痕”实现？

- 对应标记：**[假设 A3]**
- 默认建议：V1.0 不做账号、服务器和实时协作；同一用户可切换“校对者、复核者、负责人”动作身份，所有关键决定留审计记录。V1.1 再做审阅包或多人任务分派。
- 推荐理由：当前任务可由单人在本地推进；过早加入账号和同步会把大量精力转向权限、冲突、服务端和隐私，而不是校稿效率。
- 可选决策：
  - 接受建议：本地单用户。
  - 首版需要两人异步交接：增加可导入的审阅包，不做实时同步。
  - 首版需要多人实时协作：需单独设计服务端、身份、同步和冲突解决。
- 影响范围：身份系统、数据库并发、同步、审计、部署与合规。
- 不确认的阻塞：若实际必须多人同步，会改变架构；否则可按默认继续。
- 建议拍板：**接受默认建议。**

### 4. “原音确实不可辨”如何影响最终完成？

- 对应标记：**[待确认 C3]**、**[待确认 C4]**
- 默认建议：
  - 逐字层使用“[听不清 HH:MM:SS.mmm]”。
  - 用户至少记录三种听辨尝试，复核后签署“接受不可辨”。
  - 已签署的不可辨不阻塞项目完成，但在质量报告中逐条披露。
  - 成稿层可根据语义连贯性写“[原音不清]”或做有依据的编辑性删节，不能猜写。
- 推荐理由：原始声学信息可能已经永久丢失；若任何不可辨都阻塞，项目可能永远无法完成；若直接放行又会掩盖风险。单独状态和签署能兼顾诚实与可交付。
- 可选决策：
  - 接受建议：签署后可完成，报告披露。
  - 严格逐字级：任何不可辨均阻塞，直到找到更好音源。
  - 宽松编辑级：不可辨可删节，但仍需在证据层保留。
- 影响范围：疑点状态机、质量闸门、导出占位符、人工验收。
- 不确认的阻塞：阻塞“完成”定义和质量规则实现。
- 建议拍板：**接受默认建议。**

## 建议确认（影响验收完整度，但不阻塞 V0.1）

### 5. 效率目标是否定为“每音频小时人工耗时下降至少 30%”？

- 对应标记：**[待确认 C1]**
- 默认建议：保留 30% 目标，但先用同一组 60 分钟样本建立基线：清晰、一般、困难各 20 分钟。
- 需要记录：
  - 旧流程总耗时、播放器操作次数、漏存或返工次数。
  - 听校流程总耗时、平均回放次数、疑点率。
  - 校对准确性抽检结果；不能只追求速度。
- 影响范围：北极星指标之外的提效 KPI、V0.5 是否达标。
- 不确认的影响：仍可开发，但无法客观证明“更好操作”。
- 建议拍板：**先接受目标，V0.1 开始前完成基线实验。**

### 6. 现有“环境画卷”Markdown 是否作为正式导出模板？

- 对应标记：**[假设 A4]**
- 默认建议：正式支持，但以可配置模板实现；默认输出“二级标题 + 章节 + 来源文件与毫秒范围 + 正文”，先写 staging 目录，不直接改正式书稿。
- 影响范围：成稿字段、章节枚举、来源合并规则、导出验收。
- 不确认的影响：通用 Markdown 仍可实现，但后续并入当前书稿需要手工整理。
- 建议拍板：**接受默认建议。**

### 7. 性能验收线是否采用 PRD 4.3 的建议值？

- 对应标记：**[待确认 C5]**
- 默认建议：先作为工程目标；技术预研完成后，用当前 66 小时语料实测并锁定，尤其关注首次 VAD、增强代理、5 小时文件波形和精确 seek。
- 重点建议值：
  - 冷启动 P95 ≤ 5 秒。
  - 已索引文件跳转 P95 ≤ 150 ms。
  - 在真实 1,676 段样本中连续输入时，按键或 IME 组合提交到文字显示 P95 ≤ 50 ms；未修改字幕行重渲染数为 0。
  - 输入停止约 500 ms 后自动保存，刷新、页面隐藏或返回项目后文字完整一致。
  - 音文同步误差 ≤ 100 ms。
  - 支持至少 8 小时单文件、500 小时项目、500,000 段。
- 影响范围：技术方案、预计算策略、测试硬件和发布门槛。
- 不确认的影响：不阻塞功能原型，但阻塞 V1.0 性能验收。
- 建议拍板：**技术样机后确认最终数值。**

### 8. 人工质量抽检阈值是否采用“一次严重错误即退回”？

- 对应标记：**[待确认 C7]**
- 默认建议：
  - 严重错误：改变否定、数量、主体、因果、专名或核心观点；抽样中发现 1 次即退回相关文件扩大检查。
  - 普通错字率超过千分之一时，样本量加倍；第二轮仍超标则退回整文件。
  - 每文件随机抽 3 段，每段 60 秒；所有接受不可辨全部复核。
- 影响范围：人工 QA 工时和“完美文稿”验收可信度。
- 不确认的影响：系统自动规则仍可工作，但最终内容签署缺乏一致口径。
- 建议拍板：**接受默认建议，首批 3 个文件后根据真实错字分布调整。**

## 可后续补充（不阻塞 V1.0）

### 9. 产品名称是否保留“听校（TingProof）”？

- 默认建议：作为工作名保留；简短，直接表达“边听边校”，英文名便于代码仓库和包名。
- 影响范围：品牌、安装包名、应用图标和文档标题。
- 不确认的影响：无；开发可使用内部代号 tingproof。

### 10. V1.1 是否接入二次语音识别？

- 默认建议：先提供本地模型或用户自带服务配置，只允许对用户选定的短片段主动调用；结果仅做候选。
- 影响范围：模型选择、费用、API 密钥、隐私授权和网络降级。
- 不确认的影响：无；人工校对主链路完全可用。

### 11. 现场照片是否作为校稿参考资料进入项目？

- 默认建议：V1.1 支持手工关联图片与时间范围，用于识别投影片文字、人物或专名；不在 V1.0 自动按 EXIF 匹配。
- 影响范围：参考资料面板、图片索引和项目包大小。
- 不确认的影响：无；当前可从文件系统单独查看。

### 12. 是否需要脚踏板？

- 默认建议：放到 V1.2；先把快捷键配置抽象为命令映射，未来脚踏板只需映射播放、回退和确认。
- 影响范围：外设支持与测试矩阵。
- 不确认的影响：无。

### 13. 浏览器与桌面端是否必须使用完全相同的快捷键？

- 已确认目标：优先追求同一套左手快捷键，避免开发预览与正式桌面端形成两套肌肉记忆。
- 当前候选：`Ctrl+1 / Ctrl+2 / Ctrl+3` 控制当前段后退、播放/暂停、前进，`Ctrl+← / Ctrl+→` 切换字幕段，`Ctrl+E` 循环，`Ctrl+R` 创建疑点。
- 已知冲突：Chromium 通常把 `Ctrl+1/2/3` 用于切换标签页、`Ctrl+E` 用于聚焦地址栏、`Ctrl+R` 用于刷新；普通网页不能假设这些组合一定会交给页面。
- 默认建议：先做最小技术验证，分别记录普通浏览器标签页、独立 PWA 窗口与桌面壳的按键可达性；只有同一套组合在目标运行形态中均可稳定拦截，才写入正式 PRD。验证前不修改当前产品键位。
- 影响范围：桌面壳选型、开发预览方式、全局命令层、浏览器兼容、快捷键设置与自动化验收。
- 不确认的影响：不阻塞本轮“逐段播放、点击定位、行内播放”开发，但阻塞新版快捷键实现与正式验收。

## 推荐的一次性拍板结果

若希望不再开需求会、直接开始 V0.1，可采用以下默认决策：

1. 本地桌面应用，Linux 首发，项目格式跨平台。
2. 数据模型保留原始识别、逐字校对、成稿三层；V0.1 先做前两层，V0.5 补成稿。
3. V1.0 单用户，不做账号和实时同步。
4. 已签署的不可辨不阻塞完成，但必须带时间、尝试记录和质量报告披露。
5. “环境画卷”Markdown 作为可配置正式导出模板，先导出 staging。
6. 30% 提效、性能值和抽检阈值先作为目标，分别在 V0.1、技术预研和前三个试产文件后校准。

按这组决策，V0.1 可以直接进入交互原型与音频技术样机。
