### ground-truth 审计边界（V1.1.1/V1.1.2 已拍板，不再是待确认问题）

以下边界已经确认并实现（PRD §4.4.6 / AC-058 至 AC-065），列出仅为避免再次开会：

- **追加式富审计日志**：服务端 `audit_events` 为只追加（append-only）日志；只有成功写入才产生事件；409 版本冲突、400 校验拒绝与失败写入不产生事件、不增长 revision；数据写入、revision 增长与审计写入在同一事务内原子提交。**语义 no-op（V1.1.2 拍板）**：与当前持久值完全相同的 segment/issue 写入、以及分阶段补丁相互抵消后净状态无变化的 media 更新（如 durationMs 阶段被 relink 覆盖回原值），都是成功但无变化的请求——不写对象、不增长 revision、不产生审计事件，返回当前对象与当前 revision；不存在 changedFields 为空的空事件。media 的 changedFields 在全部补丁应用并 canonical 后一次性基于最终前后值计算，按白名单键序稳定排列且绝不重复。
- **事件结构**：每条事件至少包含递增 id、projectId、写入后 revision、action、objectType、objectId、timestamp、clientId、source、before、after、changedFields、metadata；before/after 是结构化 JSON 对象或 null，不以不可解析字符串暴露。
- **疑点动作分类**：区分 create_issue / update_issue / resolve_issue / reopen_issue / delete_issue；不再统一记为 upsert_issue；解决与重开保存前后完整状态；删除前完整 IssueRecord 保存在 before，after 为 null，删除后主表记录消失但事件仍可查询。**精确语义（V1.1.2 拍板）**：写返回值与审计 after 取自数据库最终行（canonical，请求省略 resolvedAt 时三处一致为 null）；已有疑点 createdAt 创建后不可变，篡改请求 400 回滚；issue_id 全局唯一，跨项目同名疑点写入 404 且双方数据/revision/审计零污染，导入碰撞与同一 create/migrate 载荷内重复 issueId 都使新项目创建整体回滚（400，不 last-write-wins），create_project 快照的 issueCount 取实际插入值、与主表 canonical 一致。
- **字幕段动作分类**：按实际前后差异区分 edit_segment_text / confirm_segment / unconfirm_segment / update_segment_timing / update_segment；一次请求同时改变多类字段时用 update_segment 且 changedFields 必须准确；原始 originalText 永不可改。
- **客户端来源不冒充身份**：当前没有账号体系，不伪造真人身份。前端携带持久但非实名的 client instance ID（浏览器 localStorage）与明确 source；服务端严格校验长度与字符集并记录；缺失 header 时诚实回退 unknown/api。clientId 可区分客户端实例，但不代表经过认证的人；账号体系后置时再升级署名语义。
- **查询 API 只读**：仅提供 GET /api/projects/:projectId/audit-events，按 id 升序稳定分页（afterId + limit，limit 有上限并严格校验，项目不存在 404）；不提供任何修改/删除审计事件的 API。**损坏即失败（V1.1.2 拍板）**：查询遇非 SQL NULL 且无法解析或类型不符的 JSON 字段时明确失败并暴露数据损坏（含事件 id 与字段），不静默置 null；SQL NULL 旧行仍诚实表示“迁移前未记录”。
- **迁移边界**：旧 SQLite 数据库（audit_events 旧 7 列）原地、幂等、无损迁移；不 drop/recreate 表、不丢旧 audit_events；新库直接为最新 schema；旧行在新增字段上保持 null；显式 schema version（PRAGMA user_version）可被测试断言。**版本只进不退（V1.1.2 拍板）**：打开数据库先读版本，高于当前程序支持版本时拒绝打开——版本号、表结构和数据保持不变（不降级、不执行当前 schema DDL）、报错明确；只有低版本才迁移。**构造失败释放句柄（V1.1.2 拍板）**：数据库成功打开之后的任何初始化异常（读取版本、PRAGMA/SCHEMA/迁移、语句预编译等，含不兼容 schema）都统一 best-effort 关闭句柄后原样重抛，不泄漏文件描述符。
- **轻量边界**：约每 5 秒的 playback 事件保持轻量、不复制大对象；项目创建、media 更新等低频事件携带合理快照。
- **本轮不做审计 UI**：接口与数据库结构即为后续 ground-truth 导出通道；界面（播放/编辑/疑点/跨设备/revision/409）语义全部保持不变。

### 删除历史记录边界（V1.1.3 已确认需求，已实现，不再是待确认问题）

- **删除对象与范围**：导入页「继续上次校对/最近项目」每条在「打开」旁提供「删除」按钮（danger 样式、白底不变，可访问名称区分项目）；确认后调用既有 `deleteProject`，在同一事务删除服务端项目行、SRT、segments、issues 与播放进度，条目从所有访问同一服务的设备上消失；不另建浏览器隐藏名单。
- **源文件零触碰**：不删除用户本机 MP3/SRT 源文件，应用内不存在任何删除源文件的代码路径。
- **审计保留**：`delete_project` 审计行（含删除前项目摘要快照）按 V1.1.2 契约继续长期保留；不新增任何审计删除接口。
- **防误删与失败语义**：行内二次确认，文案明确“将删除该项目的字幕、校对文本、疑点和播放进度，无法撤销；不会删除本机 MP3/SRT 源文件”；取消零请求、列表不变；删除期间仅目标条目按钮禁用（「删除中…」）、不阻塞其他项目、重复点击最多一次调用；成功后不整页刷新即从列表移除、总数递减、删到 0 条显示“暂无最近项目”、分页计数无负数或幽灵条目，且任何更早发出的迟到列表响应不得复活已删除条目（请求代次 + 删除失效保护，非永久 tombstone），多项目并发删除同样安全；**409 版本冲突：只安全刷新列表与 revision（绝不自动重试删除），目标项目仍存在则保留该行并提示用户重新点击「删除」并再次确认，第二次确认以最新 revision 删除成功；安全刷新失败保留当前列表与目标行（不清空）并提示稍后重试**；服务不可达等其他失败保留条目、恢复按钮、显示清晰错误且可重试，不假装已删除。
- **「打开」行为与界面简洁性不变**：主界面不新增 origin/IndexedDB 等技术说明。

### 真实标注反馈与文本预筛边界（V1.1.4 已确认需求，不再是待确认问题）

- **编辑打断精确续播**：当前段播放中聚焦当前段校对文本时在实际位置暂停；下一次同段播放从该点继续且仅这一次不应用自动回退。换段、seek、±2 秒、循环、段尾或时间轴变化清除旧标记；用户主动暂停仍保留原 1.5 秒自动回退。
- **确认自动解决本段疑点**：行内确认和 `Ctrl+Enter` 复用同一原子接口；段 confirmed 与本段全部 open 疑点 resolved 一次 revision 提交，失败整体回滚。自动解决产生带 `cause=segment_confirm` 的 `resolve_issue`；撤销确认不自动生成 reopen。
- **模型只读文本**：用户显式启动后，服务端只发送冻结范围的 `segmentId/cueNo/originalText`，不发送 MP3、音频片段、`correctedText`、本地路径或 API key。
- **候选不是事实**：模型只挑语义/疑似同音、数字日期时间、专名、断句标点可疑项；合法候选为 warning 级机器建议疑点，显示可疑片段、类型、建议、置信度与理由。模型不改稿、不确认、不创建 blocking，未报问题也不代表已审核。
- **批次与幂等**：默认 20 段一批；成功批次按 inputHash 复用，不重复调用/收费/建疑点；失败批次可续跑，刷新或服务重启不丢进度；非法 JSON、未知段、非原文子串和非法类型拒绝落库。
- **来源与降级**：机器事件 `source=machine_prefilter`，审计记录 provider/model/promptVersion/sourceTextHash/runId/batchId/candidateKey/confidence；密钥不进数据库、审计、浏览器或日志。模型未配置/不可用时人工工作流完整可用，页面继续白色底。

## 必须确认（影响架构或 V1.0 开发）

### 1. V1.0 是否确定为“局域网服务 + Linux 首发客户端”？

- 对应标记：**[假设 A1]**、**[待确认 C6]**
- 默认建议：采用由本机启动并绑定 `0.0.0.0` 的服务端，浏览器/桌面客户端通过同一服务访问；首发支持当前工作环境 Linux x86_64，项目数据格式保持跨平台，随后补 macOS 和 Windows。
- 推荐理由：跨设备的核心诉求是共享同一份进度；项目结构化数据必须放在服务端持久化，客户端只保存缓存和本设备音频关联。
- 可选决策：
  - 接受建议：可信局域网服务，Linux 首发，跨平台架构。
  - 三平台同时首发：开发和测试成本更高，排期需增加。
  - 纯浏览器本地存储：不能满足跨设备共享，不作为项目事实源。
- 影响范围：服务启动/部署、API、持久化、媒体文件重定位、客户端缓存、测试矩阵。
- 不确认的阻塞：阻塞客户端架构和 V0.1 开发。
- 建议拍板：**接受默认建议。**

### 2. V1.0 是否必须同时交付“逐字校对稿”和“可读成稿”？

- 对应标记：**[假设 A2]**、**[待确认 C2]**
- 默认建议：两层都做，原始识别层只读、逐字校对层忠实原音、成稿层负责去口语和章节化。
- 推荐理由：用户的目标是“完美文稿”，而不仅是修正字幕；若只做一层，编辑者会在“忠实原话”和“行文流畅”之间反复覆盖，证据链容易丢失。
- 可选决策：
  - 接受建议：V1.0 包含三层模型与成稿编辑。
  - V1.0 只做逐字稿：可缩短首版范围，但无法在软件内闭环产出书稿。
  - 成稿另用现有 Markdown 编辑器：听校只导出逐字稿和来源数据。
- 影响范围：数据库模型、工作台、质量规则、导出格式、V1.0 排期。
- 不确认的阻塞：阻塞核心数据模型冻结；后改成本高。
- 建议拍板：**保留成稿为 P0，但 V0.1 样机先验证逐字校对主链路。**

### 3. V1.0 是否按“单一可信服务空间、多个设备访问”实现？

- 对应标记：**[假设 A3]**
- 默认建议：MVP 面向单一可信局域网服务空间，同一责任人可从多个设备访问；暂不做完整账号/RBAC 和实时推送，但所有写入使用项目 revision 乐观锁，并保留“校对者、复核者、负责人”动作身份。
- 推荐理由：用户明确要求不同设备访问同一个服务并共享进度；身份系统可以后置，但服务端持久化和冲突保护不能后置。
- 可选决策：
- 接受建议：可信局域网单责任人，多设备访问同一服务。
  - 首版需要公网多人协作：增加账号、RBAC、HTTPS、审计、备份和实时推送设计。
- 影响范围：服务部署、数据库并发、冲突 UI、审计、身份与合规。
- 不确认的阻塞：若实际必须多人同步，会改变架构；否则可按默认继续。
- 建议拍板：**接受默认建议。**

### 4. 跨设备共享是否以同一服务端项目空间为准？

- 对应标记：**[已确认 C8]**、PRD AC-052 至 AC-057
- 已确认事实：项目归属于服务端工作空间。不同设备/浏览器只要访问同一个服务地址，就应看到同一项目列表和服务端进度；origin 不能成为数据边界。
- MVP 建议：服务端提供项目列表、项目详情、segment/issue/playback 写入和迁移 API；SQLite/WAL 或等价持久化；每次写入带 revision，冲突返回 409；刷新或短轮询即可共享，不强求首版 SSE/WebSocket。
- 音频边界：服务端保存项目元数据、SRT、校对层、状态、疑点、播放位置和版本；MP3 默认不上传，另一设备首次播放时选择或重新定位本地音频并校验指纹/时长。
- 恢复包：作为备份、服务迁移和离线兜底保留，不替代同一服务的共享事实源。
- 影响范围：API、服务端数据库、客户端仓库抽象、旧 IndexedDB 迁移、冲突 UI、部署和测试矩阵。
- 不确认的阻塞：不阻塞本轮 MVP；若需要公网多人协作，则阻塞账号/RBAC/HTTPS 的后续架构。
- 建议拍板：**接受同一服务端共享；完整账号、权限和实时推送另立后续范围。**

### 5. “原音确实不可辨”如何影响最终完成？

- 对应标记：**[待确认 C3]**、**[待确认 C4]**
- 默认建议：
  - 逐字层使用“[听不清 HH:MM:SS.mmm]”。
  - 用户至少记录三种听辨尝试，复核后签署“接受不可辨”。
  - 已签署的不可辨不阻塞项目完成，但在质量报告中逐条披露。
  - 成稿层可根据语义连贯性写“[原音不清]”或做有依据的编辑性删节，不能猜写。
- 推荐理由：原始声学信息可能已经永久丢失；若任何不可辨都阻塞，项目可能永远无法完成；若直接放行又会掩盖风险。单独状态和签署能兼顾诚实与可交付。
- 可选决策：
  - 接受建议：签署后可完成，报告披露。
  - 严格逐字级：任何不可辨均阻塞，直到找到更好音源。
  - 宽松编辑级：不可辨可删节，但仍需在证据层保留。
- 影响范围：疑点状态机、质量闸门、导出占位符、人工验收。
- 不确认的阻塞：阻塞“完成”定义和质量规则实现。
- 建议拍板：**接受默认建议。**

## 建议确认（影响验收完整度，但不阻塞 V0.1）

### 6. 效率目标是否定为“每音频小时人工耗时下降至少 30%”？

- 对应标记：**[待确认 C1]**
- 默认建议：保留 30% 目标，但先用同一组 60 分钟样本建立基线：清晰、一般、困难各 20 分钟。
- 需要记录：
  - 旧流程总耗时、播放器操作次数、漏存或返工次数。
  - 听校流程总耗时、平均回放次数、疑点率。
  - 校对准确性抽检结果；不能只追求速度。
- 影响范围：北极星指标之外的提效 KPI、V0.5 是否达标。
- 不确认的影响：仍可开发，但无法客观证明“更好操作”。
- 建议拍板：**先接受目标，V0.1 开始前完成基线实验。**

### 7. 现有“环境画卷”Markdown 是否作为正式导出模板？

- 对应标记：**[假设 A4]**
- 默认建议：正式支持，但以可配置模板实现；默认输出“二级标题 + 章节 + 来源文件与毫秒范围 + 正文”，先写 staging 目录，不直接改正式书稿。
- 影响范围：成稿字段、章节枚举、来源合并规则、导出验收。
- 不确认的影响：通用 Markdown 仍可实现，但后续并入当前书稿需要手工整理。
- 建议拍板：**接受默认建议。**

### 8. 性能验收线是否采用 PRD 4.3 的建议值？

- 对应标记：**[待确认 C5]**
- 默认建议：先作为工程目标；技术预研完成后，用当前 66 小时语料实测并锁定，尤其关注首次 VAD、增强代理、5 小时文件波形和精确 seek。
- 重点建议值：
  - 冷启动 P95 ≤ 5 秒。
  - 已索引文件跳转 P95 ≤ 150 ms。
  - 在真实 1,676 段样本中连续输入时，按键或 IME 组合提交到文字显示 P95 ≤ 50 ms；未修改字幕行重渲染数为 0。
  - 输入停止约 500 ms 后自动保存，刷新、页面隐藏或返回项目后文字完整一致。
  - 音文同步误差 ≤ 100 ms。
  - 支持至少 8 小时单文件、500 小时项目、500,000 段。
- 影响范围：技术方案、预计算策略、测试硬件和发布门槛。
- 不确认的影响：不阻塞功能原型，但阻塞 V1.0 性能验收。
- 建议拍板：**技术样机后确认最终数值。**

### 9. 人工质量抽检阈值是否采用“一次严重错误即退回”？

- 对应标记：**[待确认 C7]**
- 默认建议：
  - 严重错误：改变否定、数量、主体、因果、专名或核心观点；抽样中发现 1 次即退回相关文件扩大检查。
  - 普通错字率超过千分之一时，样本量加倍；第二轮仍超标则退回整文件。
  - 每文件随机抽 3 段，每段 60 秒；所有接受不可辨全部复核。
- 影响范围：人工 QA 工时和“完美文稿”验收可信度。
- 不确认的影响：系统自动规则仍可工作，但最终内容签署缺乏一致口径。
- 建议拍板：**接受默认建议，首批 3 个文件后根据真实错字分布调整。**

### 10. 文本预筛生产环境使用哪一个 provider/model？

- 对应标记：**[待确认 C11]**；功能边界与接口已经按 V1.1.4 确认，本项只决定真实模型联调和费用/隐私落点。
- 默认建议：首版实现服务端 OpenAI-compatible adapter，以 `TINGPROOF_LLM_BASE_URL`、`TINGPROOF_LLM_MODEL`、`TINGPROOF_LLM_API_KEY` 配置；优先使用本地或用户自带服务。自动测试使用可注入假模型，不依赖公网、不消费真实额度。
- 已确认的固定边界：浏览器不保存 key；默认不主动调用；用户点击开始后只发送原始 ASR 文本，不发送音频或人工稿；候选只作 warning 建议。
- 可选决策：
  - 本地 OpenAI-compatible 服务：隐私最好，需确认模型中文能力和机器资源。
  - 用户自带云服务：部署简单，但需确认数据处理条款、费用和限流。
  - 暂不配置：入口显示“机器预筛未配置”，人工校对不受影响；功能契约和假模型测试仍可交付。
- 影响范围：部署环境变量、真实模型联调、隐私说明、速率/费用上限与 prompt 评估基线。
- 不确认的影响：不阻塞代码、数据库迁移和自动化验收；阻塞真实项目点击“开始预筛”后拿到生产模型结果。
- 建议拍板：**先按 OpenAI-compatible + 本地/用户自带服务实现，真实 provider/model 后填。**

### 11. 产品名称是否保留“听校（TingProof）”？

- 影响范围：模型选择、费用、API 密钥、隐私授权和网络降级。
- 不确认的影响：无；人工校对主链路完全可用。

### 13. 现场照片是否作为校稿参考资料进入项目？

- 默认建议：V1.1 支持手工关联图片与时间范围，用于识别投影片文字、人物或专名；不在 V1.0 自动按 EXIF 匹配。
- 影响范围：参考资料面板、图片索引和项目包大小。
- 不确认的影响：无；当前可从文件系统单独查看。

### 14. 是否需要脚踏板？

- 默认建议：放到 V1.2；先把快捷键配置抽象为命令映射，未来脚踏板只需映射播放、回退和确认。
- 影响范围：外设支持与测试矩阵。
- 不确认的影响：无。

### 15. 浏览器与桌面端是否必须使用完全相同的快捷键？

- 已确认目标：优先追求同一套左手快捷键，避免开发预览与正式桌面端形成两套肌肉记忆。
- 当前候选：`Ctrl+1 / Ctrl+2 / Ctrl+3` 控制当前段后退、播放/暂停、前进，`Ctrl+← / Ctrl+→` 切换字幕段，`Ctrl+E` 循环，`Ctrl+R` 创建疑点。
- 已知冲突：Chromium 通常把 `Ctrl+1/2/3` 用于切换标签页、`Ctrl+E` 用于聚焦地址栏、`Ctrl+R` 用于刷新；普通网页不能假设这些组合一定会交给页面。
- 默认建议：先做最小技术验证，分别记录普通浏览器标签页、独立 PWA 窗口与桌面壳的按键可达性；只有同一套组合在目标运行形态中均可稳定拦截，才写入正式 PRD。验证前不修改当前产品键位。
- 影响范围：桌面壳选型、开发预览方式、全局命令层、浏览器兼容、快捷键设置与自动化验收。
- 不确认的影响：不阻塞本轮“逐段播放、点击定位、行内播放”开发，但阻塞新版快捷键实现与正式验收。

## 推荐的一次性拍板结果

若希望不再开需求会、直接开始 V0.1，可采用以下默认决策：

1. 同一服务端项目空间作为事实源，绑定 `0.0.0.0` 供可信局域网访问；Linux 客户端首发，项目格式跨平台。
2. 数据模型保留原始识别、逐字校对、成稿三层；V0.1 先做前两层，V0.5 补成稿。
3. V1.0 面向单一可信服务空间，可由多个设备访问；暂不做完整账号/RBAC 和实时推送，但必须有服务端持久化、revision 冲突保护和幂等迁移。
4. 已签署的不可辨不阻塞完成，但必须带时间、尝试记录和质量报告披露。
5. “环境画卷”Markdown 作为可配置正式导出模板，先导出 staging。
6. 30% 提效、性能值和抽检阈值先作为目标，分别在 V0.1、技术预研和前三个试产文件后校准。
7. ground-truth 审计按 V1.1.2 契约执行（追加式富审计、动作分类、非实名 clientId、只读分页查询、旧库原地幂等迁移且版本只进不退、语义 no-op 不产生事件——含 media 分阶段补丁净 no-op 且 changedFields 按最终值一次性计算不重复、createdAt 不可变、issue_id 全局隔离——含同一载荷内重复 issueId 整体回滚且 create_project 快照 issueCount 与主表一致、数据库 open 后任意初始化失败统一释放句柄后原样重抛、损坏 JSON 明确失败；本轮不做审计 UI）。
8. 删除历史记录按 V1.1.3 契约执行（导入页行内二次确认后服务端硬删除并跨设备消失；本机源文件零触碰；delete_project 审计行保留、不新增审计删除接口；409 冲突安全刷新 revision 后由用户再次确认，绝不自动删除；迟到列表响应不产生幽灵条目；其他失败保留条目可重试；「打开」行为不变）。
9. V1.1.4 三项真实标注反馈按已确认口径执行：编辑打断精确无回退续播；确认与本段 open 疑点解决同事务且撤销不自动重开；文本预筛只读 originalText、批次幂等可恢复、候选为可审计 warning 疑点、失败不影响人工校对。
10. 生产 provider/model 暂按 OpenAI-compatible adapter + 服务端环境变量留口；自动测试使用假模型。未配置真实模型时如实显示不可用，不在浏览器收集密钥。

按这组决策，V0.1 可以直接进入服务端 API、双客户端共享探针、音频技术样机与文本预筛契约实现；人工标注和机器候选的 ground truth 可直接从审计查询 API 对照导出。
